### 2.2 D-22：`MUST = N` 到底算不算错误？——我方最终立场

这是本次磋商里最需要给出明确立场的一条。

**事实层面（双方一致，已实测）**：`lengthCapability[^.]*MUST be set to` 在 bcgr/egdi 均 **0 命中**。规范对 `lengthCapability` 只有一句：
`A 16-bit, unsigned integer. The length in bytes of the capability data, including the size of the capabilitySetType and lengthCapability fields.`（2336 等 23 处）

**结构层面**：2.2.7.x 每节的字段表把每个字段宽度写死（`(2 bytes)`、`(16 bytes)`…），所以**总长是唯一确定的**。General 只能是 24，不可能是别的值——这是**结构推论**，强度等价于 MUST，但**没有 MUST 字样**。

**我的最终立场**：**「表述不当」，不是「事实错误」**。理由：
1. 文档 §8 的**数值全部正确**（我 A 项已 27/27 逐字段验证），写 `MUST = 24` 不会误导实现者写出错的值。
2. 错的是**规范强度标签**：把"结构推论"标成"规范 MUST"，会让读者以为规范原文有这么一句，去原文找不到。
3. 但 U-20 的**原因栏**（"各 capability 节都写 MUST be set to N"）是**事实错误**——它把文档自己的措辞当成规范原文来引证。这一句必须改。

**因此修不修**：**要修，但只改措辞，不改数值**。建议：
- §8 各节：`MUST = 24` → `定长 24（由字段宽度推出；规范未对该字段取值作 MUST 规定）`
- U-20 原因栏：改为「规范未固定 `lengthCapability` 取值；各节字段宽度决定期望总长；接收侧按实际值定界，`len < 期望` 时缺失字段取 0 并告警」

**与乙的分歧**：乙 D-22 建议"§8 统一改为 定长 24（结构推导；规范未固定该值）"——**方向正确，我同意**。乙没有明说"这算表述不当还是事实错误"，我用本节给出定性，以便执行 AI 知道**只改标签、不动数值**（避免误删正确的长度值）。

### 3.2 §14.1 红证：是 26 还是 28 字节？

**裁定：取决于注入方式，两个数都对，但只有 28 能对应文档自述的原因。**

文档 §14.1 行 2304–2309 声称：第一版把 General 写成「13 项（**多算了一个 `pad2octets`**）」→ `expect=28`。
`verify_caps.py` 的 `LEN = {c[1]: (c[0], 4 + sum(c[2]), c[3])}`（行 46）**已自动加 4 字节头**，所以 payload 宽度表只应含 capabilityData。

我做了两组注入（`a_redgreen.py`，实跑输出）：

```
== red_doublecount.py   (payload 里把 capabilitySetType + lengthCapability 也算进去 → 4 + 24 = 28)
      cap[ 1] General  len=24  expect=28  FAIL
== red_onepad.py        (payload 里只多加一个 2 字节 pad2octets → 4 + 22 = 26)
      cap[ 1] General  len=24  expect=26  FAIL
== green_orig.py
      cap[ 1] General  len=24  expect=24  PASS
```

- **26** = payload 多一个 2 字节字段（= 文档自述的"多算了一个 pad2octets"）
- **28** = payload 把两个头字段也计入，被 `4 +` 二次计入（double-count）

**所以文档的"多算一个 pad2octets → 28"在算术上不成立**：多一个 2 字节只能得 26。要得 28 必须双计两个头字段（4 字节）。红证的方向（错模型必被 dump 打回）成立，**归因错误**。这条已并入合并清单 **M-3**。

### 9.3 三处严重度分歧的裁定（经第三轮机械仲裁定案）

> **本节已按父会话第三轮的机械仲裁改写。** 上一版（第二轮）我把 F-03/F-12 定为"严重"、把 F-06 定为"一般"，
> **这三处都被仲裁推翻**。以下为定案版本，被推翻的理由保留在 §11.2 的让步记录里，不在此处粉饰。

#### 分歧 1：§6.1 遍历缺上界（F-03 / F-12）—— **定案：均判阻断**

**裁定：F-03 = 阻断，F-12 = 阻断。我原先的"严重"是低估。**

判据不是"改动量小"，而是**共同定义的分支 (b)**：`可被对端触发的内存越界/崩溃`。红证（`F:\rtsc\evidence\capabilities\redlit_walk.exe`，实跑输出，已固化在仓库内）：

```
A count>data (F-12)          doc=OOB-READ-HEADER    off=24 len=4 end=24 | fix=ERR-header-oob
B len>remaining (F-03)       doc=OOB-READ-BODY      off=0 len=200 end=8 | fix=ERR-body-oob
C legal (green)              doc=OK                 off=24 len=0 end=24 | fix=OK
```

- **场景 B（F-03）**：`lengthCapability = 200`，`caps` 区只剩 8 字节 → `process()` 消费 200 字节，越过接收缓冲区末尾 → 越界读。
- **场景 A（F-12）**：`numberCapabilities = 3`，实际只有 1 个 24 字节 set → 第二轮循环时 `p = 24` 已等于 `end = 24`，伪码仍继续 `LE16(p)`/`LE16(p+2)` → 越界读。
- **两者都由对端字段直接控制**，无本地前置条件 → 命中 (b) → 阻断。

**我原先"不判阻断"的理由错在哪**：我写的是"合法输入下能跑通（场景 C），所以不是阻断"。这是把阻断的 (a) 分支（功能完全不工作）当成了唯一入口，**漏掉 (b) 分支**。定义里 (a)/(b) 是**或**关系，(b) 独立成立即可判阻断。我用"正常输入能跑通"去否定 (b)，是**判据错位**，不是事实分歧。

#### 分歧 2：持久缓存清空（F-06 / F-07）—— **定案：F-06 严重 / F-07 一般**

**裁定：F-06 = 严重。我第二轮的"一般"也是低估；乙第一轮的"一般"同样低估。**

- 后果链：照字面清空 Persistent Bitmap Cache → 违反 `bcgr.txt:7212`（`Persistent Bitmap Caches are not bound to the lifetime of a given RDP connection`）→ 服务端仍按旧 key 引用槽位 → 客户端发 `Bitmap Cache Error`（`egdi.txt:3755` SHOULD）→ 服务端重绘后恢复。
- **不命中 (a)**：连接仍可用，画面可恢复。
- **不命中 (b)**：是"多丢数据"，不是越界。
- **但命中"严重"档的"错误行为"**：它明确改变运行时行为（缓存被错误清空 + 触发 flush 重绘），而"一般"档的定义明写**不改变字节与行为**。既然改变了行为，就**不能留在一般**。
- **F-07 保持一般**：它只是缺一段"清空的代价"说明，本身不改变行为，属表述缺失。

#### 分歧 3：Fast-Path dump 明文冒充密文（F-02）—— 甲判"高"，乙判"严重"

**裁定：严重。接受乙。**

关键事实：文档**自己在 §3.4 行 543 写的是正确密文** `26 18 5e 76 0e de 28`（`bcgr.txt:11569/11581`），只有 §13.4 行 2162-2163/2171 写成了解密后载荷 `20 00 08 ab 02 6f 01`（`bcgr.txt:11583`，原文明确标注 `Decrypted`）。所以：

#### 11.3.6 `WouldRead()` 的性质（不是缺陷）

`WalkDoc` 用 `WouldRead(off, n, size)` 在每次"读"前判断"这一读会不会越过末尾"，**而不去真读越界内存**——这是 harness 的必要安全设计。由此 harness 报的 `OOB-READ-*` 是**建模结论**（"此处本会越界"），不是"真的访问了越界内存"。

我用**完全无上界检查**的独立逐字实现（`a_r4_literal.py` / `a_r5_verify6.py`，只判断"是否将读越界"）复核，A/B 同样成立。加上乙的 `r3_probe.py`（越界即抛 `IndexError`），**三份独立实现对 A/B 结论一致** → F-03/F-12 命中 (b) 稳健，不依赖任何单一 harness 的建模方式。

**方法学结论（三条，按发现顺序）**：

1. **判据必须对着「什么是正确」写，不是对着「旧值是什么」写。** 我前几版判据把「旧值消失」当成了「正确」，结果在文档已正确改写的地方误报（第 1、4 处）。
2. **判据必须表达「语义要求」，不能表达「当前实现的快照」。** 这条由 F-29 暴露：我最初把判据写成「§0.2 的计数必须等于 87」，而正确做法是「计数必须等于**实际抓取的 learn 页数**」——数字会随来源表扩充而变（实测已从 87 变 97），绑死数字的判据必然过期。同理 F-35 不能绑死「某处不得出现某词」，而要表达「顺序约束不得表述为严格串行」。
3. **判据设计时必须回看「最小修正」的【全部】选项。** 这条由第 6 处暴露：F-30 的方案给了两个选项，我的判据只接受其中一个，于是把「照方案执行」判成 FAIL。**规则**：若判据只接受方案的一部分选项，**必须在判据里写明理由**。本例理由成立（选项②未消除标题-内容矛盾），但当时没写，导致执行 AI 与父会话都需要额外一轮核对才发现「方案本身有缺陷」。

**这六条修正都是我的错，不是文档的错**（第 6 处例外：它抓到了方案本身的缺陷）。记录在此，避免执行 AI 被错误判据误导去改本来正确的文字。
