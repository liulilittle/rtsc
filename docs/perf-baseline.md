# RTSC Performance Baseline

Reproducible performance baseline for RTSC's rendering hot paths, built for the
user's hard constraint **"极致性能（远程桌面 CPU 不炸）"** (extreme performance:
the remote-desktop CPU must not be pinned).

All numbers in this document are produced by `tools/rtsc_bench/main.cpp`
(`rtsc_bench.exe`) and captured from real runs. Nothing is estimated or copied
from elsewhere.

## 1. Environment

| Item | Value |
| --- | --- |
| OS | Windows 10/11 (`_WIN32`), Windows SDK 10.0.26100.0 |
| Compiler | MSVC 1944 (Visual Studio 2022, vcvars MSBuild 17.14.60) |
| Generator | Visual Studio 17 2022, config `Release` |
| Optimization | `NDEBUG` (Release) — MSVC default `/O2` for `Release` |
| Arch | x86_64 |
| Fixed frame | 1920x1080 (2,073,600 px, 8.29 MB RGBA8888) |
| TLS | scripted loopback (same in-memory transport as `tests/test_security_layer.cpp`) |

## 2. Build and run

```powershell
cmake --build build --config Release          # 0 errors, 0 warnings
.\build\Release\rtsc_bench.exe                 # writes the report tables below
```

Build evidence (full Release build, `2026-10-26`):

```
$ cmake --build build --config Release
error count: 0
warning count: 0
rtsc_bench.vcxproj -> F:\rtsc\build\Release\rtsc_bench.exe
```

Methodology: every codec is generated from a **fixed deterministic pattern**
(no RNG), warmed up (3 iterations), then timed **30 times**; the reported time is
the **median** of those runs, with min / max / mean / stddev alongside. Throughput
`MB/s` uses the input stream size for `in(MB/s)` and the decoded RGBA8888 size
(`width*height*4`) for `out(MB/s)`; `fps` is `1 / median`.

## 3. Bitmap decode throughput (1920x1080)

Input stream for each codec is generated by `main.cpp` (see
`MakeRaw32`, `MakeRle16`, `MakeRdp6Argb`, `MakeRdp6AyCoCg`, `MakeNsc`). The RLE
input mixes long colour runs and raw colour images; the RDP6/NSCodec inputs use
raw (uncompressed) planes. The "canonical" run is the first invocation after the
build; two further independent runs are listed to show run-to-run variance.

### 3.1 Canonical run (median of 30 timed iterations)

| codec | in(MB) | median | min | max | stddev | in(MB/s) | out(MB/s) | fps |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| raw-32bpp | 8.29 | 4.238 ms | 3.978 ms | 4.746 ms | 0.245 ms | 1957.1 | 1957.1 | 236.0 |
| rle-16bpp | 2.17 | 8.267 ms | 7.787 ms | 9.768 ms | 0.535 ms | 262.5 | 1003.4 | 121.0 |
| rdp6-argb | 8.29 | 5.418 ms | 4.975 ms | 6.514 ms | 0.365 ms | 1530.8 | 1530.8 | 184.6 |
| rdp6-aycocg | 6.22 | 7.004 ms | 6.584 ms | 9.036 ms | 0.503 ms | 888.2 | 1184.2 | 142.8 |
| nsc-aycocg-cs | 5.18 | 6.589 ms | 6.042 ms | 9.916 ms | 0.928 ms | 786.8 | 1258.9 | 151.8 |

### 3.2 Independent re-runs (median frame time / fps)

| codec | run A median / fps | run B median / fps | run C median / fps |
| --- | ---: | ---: | ---: |
| raw-32bpp | 4.238 ms / 236.0 | 5.205 ms / 192.1 | 5.249 ms / 190.5 |
| rle-16bpp | 8.267 ms / 121.0 | 9.421 ms / 106.1 | 9.494 ms / 105.3 |
| rdp6-argb | 5.418 ms / 184.6 | 5.805 ms / 172.3 | 6.043 ms / 165.5 |
| rdp6-aycocg | 7.004 ms / 142.8 | 7.752 ms / 129.0 | 7.755 ms / 129.0 |
| nsc-aycocg-cs | 6.589 ms / 151.8 | 7.016 ms / 142.5 | 7.283 ms / 137.3 |

**Observation.** The first run after process start is consistently fastest (the
OS page cache and allocator are hot and the CPU is at its boost clock); later
runs settle ~10–15% slower. The benchmark therefore reports the median of the
timed iterations within one run, and the three-run table makes the drift
explicit rather than hiding it.

**Relative cost (canonical run):**

- raw 32bpp is the cheapest decode (a memcpy + row-reversal), as expected.
- rle-16bpp is the **most expensive** (8.267 ms, 121 fps): Interleaved RLE is
  byte-order driven and the pattern mixes many colour images.
- rdp6-argb (5.418 ms) is ~28% faster than rdp6-aycocg (7.004 ms), because the
  AYCoCg path additionally expands chroma and applies the inverse YCoCg
  transform per pixel.
- nsc-aycocg-cs (6.589 ms) sits between them; it also does chroma expansion +
  inverse transform, plus the 8-byte-aligned luma stride.

## 4. End-to-end loopback latency (scripted TLS)

A full-screen 1920x1080 update is tiled into **300** fast-path PDUs (96x72 tiles,
RDP6 ARGB raw planes). The fast-path length field is 15 bits, so a full-screen
frame does not fit in a single PDU and must be split — which is what a real
server does.

The security layer is driven through TLS -> CredSSP -> EUAR with the scripted TLS
transport (identity Send/Receive), the same loopback the security tests use.

| measurement | run A | run B | run C |
| --- | ---: | ---: | ---: |
| frame PDUs | 300 | 300 | 300 |
| round-trip (encrypt+decrypt), median | 0.814 ms | 0.857 ms | 0.833 ms |
| round-trip min / max | 0.763 / 1.102 ms | 0.791 / 1.369 ms | 0.775 / 1.001 ms |
| round-trip mean / stddev | 0.859 / 0.108 ms | 0.893 / 0.123 ms | 0.843 / 0.059 ms |
| effective loopback throughput | 10193.4 MB/s | 9678.4 MB/s | 9954.9 MB/s |
| end-to-end frame (transport+parse+decode) | 5.428 ms (184.2 fps) | 5.561 ms (179.8 fps) | 7.738 ms (129.2 fps) |

The scripted TLS transport is the identity, so the round-trip measures the
security layer's framing overhead (TPKT / fast-path peeling, record accounting)
and buffer copies, not real crypto. The end-to-end number adds fast-path
parsing and the graphics-pipeline decode of all 300 tiles into the client's
1920x1080 surface. Frame-to-frame latency is therefore ~5.5 ms (~180 fps) on the
canonical run, dominated by the decode (the transport is ~0.8 ms).

Sanity check printed by the tool: the center pixel after the full frame decode
is `rgba(56,93,130,19)`, matching the generated RDP6 ARGB planes.

## 5. Process CPU occupancy

`std::clock()` (process CPU time) divided by wall time
(`std::chrono::steady_clock`), measured while decoding the RDP6 ARGB stream for a
fixed 2.0 s wall window.

| run | frames | fps | CPU time | wall time | occupancy |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 337 | 168.1 | 2.005 s | 2.005 s | 100.0% |
| B | 326 | 162.6 | 2.005 s | 2.005 s | 100.0% |
| C | 343 | 171.1 | 2.005 s | 2.005 s | 100.0% |

**Interpretation.** Occupancy is exactly 100% — the decode workload is a single
thread pinned at one full core, which is the expected steady-state for a
CPU-bound decode loop with no I/O or sleep. At ~168 fps for a 1920x1080 RDP6
ARGB frame, the decoder consumes one core and never idles, so a full-screen
stream at this rate will hold one core at 100%. This is the number that matters
for the "CPU 不炸" requirement: the decoder itself is single-threaded and
saturates a core by design, so the practical CPU cost is bounded and predictable
(~1 core per full-screen RDP6 frame stream).

## 6. Conclusions

- All five bitmap paths decode a 1920x1080 frame well above 60 fps; the slowest
  (Interleaved RLE at 16bpp) still reaches 121 fps, the fastest (raw 32bpp)
  236 fps.
- End-to-end frame latency over the scripted TLS loopback is ~5.5 ms
  (~180 fps), dominated by decode; the transport framing is ~0.8 ms.
- CPU occupancy is a flat 100% on one core during a sustained decode — the
  workload is single-threaded and CPU-bound, so it cannot exceed one core by
  itself. This is the baseline to compare any future multi-frame/optimized
  decoder against.

## 7. Reproducibility

- Fixed inputs: generated from arithmetic patterns, no RNG (see §3).
- Warm-up: 3 iterations discarded before timing.
- Median: each codec's time is the median of 30 timed iterations; run-to-run
  variance is reported in §3.2.
- The tool is read-only with respect to product code: it only links the public
  libraries and the test TLS seam (`SetTlsTransportForTest`).

### Known limits

- RDP6 and NSCodec are measured with **raw (uncompressed) planes**; the RLE-plane
  variants of those two codecs are not exercised here (the raw path isolates the
  plane assembly + colour transform, which dominates decode time).
- The scripted TLS loopback replaces real SChannel/OpenSSL, so the round-trip
  does not include cryptographic cost. It measures the framing overhead only.
- Numbers are specific to the environment in §1 (MSVC 1944, Release, Windows 11
  host). Re-run on another host will produce different absolute values; the
  tool exists so each host can regenerate its own baseline.
