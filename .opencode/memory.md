# RTSC 记忆（memory.md）

## 项目本质
RTSC = mstsc 逆向重写（Reverse To Source Client）。以 Windows 官方 RDP 客户端
mstsc.exe + mstscax.dll 为逆向对象，用 C++ 跨平台重写，最终支持 Windows 与 Linux。

## 多平台路线（2026-10-23 用户明确指示）

**用户原话**：「先逆向成 C++ 没有问题后我们要考虑 Android/其它平台」
「就是跨平台实现，但先把 Windows 版本搞正确没问题」。

### 顺序（不可颠倒）
1. **先把 Windows 版做正确**（当前阶段）：协议正确性、SChannel 后端、CredSSP、实机连通。
2. **之后**扩 Android / Linux / macOS。**不是现在并行做**。

### 但架构必须从一开始就为跨平台留位（零成本前置）
这些约束**现在就要遵守**，因为事后改造代价远大于当下遵守：

| 约束 | 现状 | 要求 |
|---|---|---|
| 协议层零平台依赖 | ✅ 已满足：`src/proto/*`、`src/crypto/*` 无任何 Windows 头 | 禁止在 proto/crypto 引入平台 API |
| 字节序显式移位 | ✅ 已满足：`byte_order.cpp` 全用 `<<`/`|` 手工拼，无 `htonl`/`__builtin_bswap`/`memcpy` 到整数 | 禁止用平台字节序函数；ARM 大端/小端都必须对 |
| 平台耦合集中隔离 | ✅ 仅 `src/util/crash_guard.cpp` 一处 `#ifdef _WIN32`，且已提供非 Windows no-op | 新平台代码必须新建文件，不得在既有文件里加 `#ifdef` 分支 |
| TLS 后端接口化 | 🔄 `TlsTransport` 纯虚接口已设计（`design-a.md`） | Windows=SChannel，Linux/Android=OpenSSL/BoringSSL，**禁止**把 SChannel 类型泄漏进接口 |
| 测试可跨平台 | ✅ 12 套件全用自研 CHECK 宏，无 gtest/Catch 依赖 | 禁止引入需平台适配的测试框架 |
| CMake 平台分支 | ⚠️ 现为 `if(MSVC)` 加 `/W4 /WX`；`target_link_libraries(rtsc_util PUBLIC dbghelp)` 在 MSVC 内 | 新平台用 `if(CMAKE_CXX_COMPILER_ID MATCHES ...)`，不得假设 MSVC |

### 已知的 Android 特有约束（现在记下，实施时验证）
- **TLS**：Android 系统无 OpenSSL 公开 API，需 BoringSSL（NDK 自带）或自编译 OpenSSL；**不可**假设有 SChannel。
- **证书库**：SChannel 的 `CertCreateSelfSignCertificate`（自签测试用）无对应物，需 BoringSSL 的 `X509` API 或测试期静态证书。
- **字符编码**：Android 全 UTF-8，`wchar_t` 是 4 字节（Windows 是 2 字节）→ **禁止**在协议层用 `wchar_t` 表达 UTF-16；现有 `client_info.cpp` 已有显式 UTF-16LE 编码函数，正确。
- **线程/网络**：Android 用 POSIX socket + pthread；`std::thread` 可用（libc++ 支持）。
- **崩溃取证**：`crash_guard` 的 dbghelp 路径在 Android 需换为 `debuggerd`/`tombstone`，但这是**开发期工具**，不影响产品代码。

### 架构分层目标（最终形态）
```
include/rtsc/proto/   协议编解码（纯数据，零平台依赖）
include/rtsc/crypto/  密码学原语（MD4/MD5/SHA1/HMAC/RC4/NTLM）
include/rtsc/net/     传输抽象：ITransport（socket）、TlsTransport（TLS）
src/net/win/          SChannel 后端 + Winsock ITransport
src/net/posix/        OpenSSL/BoringSSL 后端 + POSIX ITransport
src/net/android/      平台特定（JNI 桥、证书库适配）
```

## 方法论
1. 双证据源：官方规范（[MS-RDPBCGR] 等）+ 二进制取证（Ghidra/REA）；二者冲突时以
   真实抓包（pktmon）裁决。
2. 分层实现：TPKT → X.224 → MCS(T.125) → 安全层 → 能力交换 → 图形/输入/通道。
3. 每层 TDD：先写规格测试（红）→ 最小实现（绿）→ 重构。
4. 每条协议常量/字段必须能追溯到规范章节或 Evidence 地址。
5. **文本检查与结构检查是两类不同手段，不可互相替代**（2026-10-23 沉淀）：
   - 文本层（doc-lint、残留扫描、正则判据、变异测试）只能发现"字写错了/漏了/不一致"。
   - **控制流结构缺陷（缺回边、变量未定义、状态入口检查与返回点不自洽）会被文本检查全部放过**。
     实例：design-a 的 B1（成功路径无 `continue` → 一次 Receive 只解一条）、
     B2（`extra_len` 从未定义）、B3（`kClosed` 不置 `terminal_` 却承诺幂等），
     三条阻断**全部通过**了 doc-lint(fail=0) + 残留扫描。
   - 伪代码/代码必须**逐路径走查**：列出全部出口与回边，对每个出口断言
     「资源是否已消费」「输出是否已正确累加」「返回值是否符合契约」。
6. **位置类缺陷只能靠执行路径模拟发现**：连续两轮静态审阅都可能放过同一处
   （乙两次读 design-a `plaintext_out.clear()` 都当成"失败路径保护"，
   因为它位置在循环体内才出错）。**"模拟 N 条数据逐迭代走一遍"是唯一可靠手段。**
7. 审计方与被审方**都要能自我更正**：本项目已出现多次"审计 AI 判错后主动撤回"
   （乙撤回 D14、更正绿证 8 机制分析、承认 N5 是自身遗漏），
   以及"主代理判断错误被子代理纠正"（我的"原伪代码也能返回 kOk"分析被乙推翻）。
   **正确性属于团队，不属于角色权威。**

## 改文件与汇报的硬规则（2026-10-23 三次失实后沉淀）

本项目已发生 **3 次「汇报已改但实际未落地」**（`:88` 一次、`kOk_WITH_CLOSED_FLAG` 两次）。
根因两类：①写了替换代码但没跑就汇报；②`assert` 失败被后续串联命令掩盖。
以下 4 条为硬规则，**违反即视为未完成**：

1. **汇报「已改」必须附「改后文件的实际状态」，不是「我写了什么代码」**。
   - ❌「已改为 `re.match(r'^st\b', cond)`」← 这是意图
   - ✅「读回文件：`re.match(r'^st\b'` 命中 :91；`'st' in cond` 仅注释 1 处」← 这是事实
   - 成本 +1 次读回，第 1 类失实归零。

2. **每处替换必须双向断言 + 读回**：
   ```python
   if old not in L[idx]: raise SystemExit(1)      # 锚点失效立即停
   L[idx] = L[idx].replace(old, new)
   # 写完读回
   chk = io.open(p, encoding='utf-8').read()
   assert old_pattern_gone(chk) and new_pattern_present(chk)
   ```
   只检查「旧串在不在」不够，必须检查「替换后旧串是否消失」。

3. **禁止用 `python -c` 串联多个操作**。改文件/验证一律独立脚本文件，
   一次一件事，退出码即结论；PowerShell 侧逐条 `if ($LASTEXITCODE -ne 0) { exit 1 }`。
   **「命令链最后一行成功」≠「每一行都成功」。**

4. **每条正则/锚点检查必须配「等价写法」红证**。
   同一语义至少测三种写法：①行首 `^\s*X` ②`;` 分隔 `; X` ③跨行。
   实例（G8）：`closed_=true; pass`（同行）曾漏检，而伪代码自己就在用 `closed_ = true; return kClosed` 同行写法。
   **锚点是正则最易出错处，且只在特定写法下暴露。**

5. **「变异被检出」≠「检查机制生效」**。
   若变异同时改变了被 EXPECT 比对的动作，报错可能来自上层比对而非下层检查（「顺带检出」）。
   验收新增检查时，必须有**直接调用检查函数**的测试，绕开 evaluate/EXPECT/main。
   实例：`verify_sideeffect_leaf.py` 直接调 `_classify_leaf()`。

6. **门禁文件的缺失必须 FAIL，不能静默 skip**。
   实例（G9）：`verify.ps1` 预检漏了 `$side`/`$csr`，删掉检查器文件后门禁仍通过。
   所有门禁脚本必须先进 `foreach ($f in @(...)) { if (-not (Test-Path $f)) { exit 1 } }`。

## 正则锚点与证据的补充规则（2026-10-23 第 15-16 轮沉淀）

7. **扫锚点缺陷时，必须同时扫「有锚点的」和「该有锚点却没有的」**。
   实例：`return\s+kClosed`（完全无锚点）= 全文任意位置匹配，比 `^\s*` 更宽松，
   但在同行写法下恰好能匹配，所以不暴露。只扫 `^\s*` 会漏掉它。

8. **禁止"确认偏误式"的证据声明**。
   反例（consult-b 自查发现）：「我全文扫了锚点」实际方法是「过滤含 `^\s*` 的行」，
   等于只扫了预期要扫的。**说"全文扫"就必须真的遍历全文，且声明所用方法。**
   正确表述：「按 `^\s*` 模式过滤后扫了 N 行，另按无锚点模式复扫得 M 行」。

9. **正则锚点必须覆盖 5 种语句写法**（同一语义的等价形式）：
   ①行首 `^\s*X` ②`;` 分隔 `; X` ③同行+注释 `X # c`
   ④**内联 `if c: X`** ⑤跨行。少测任何一种，就有一类写法静默漏检。
   实例：G8 漏了 ②，G10 漏了 ④，两次都是同一类错误。

10. **验证脚本的断言过程必须落盘为证据，脚本本身可以删**。
    反例：fix 脚本运行时的读回断言不可复核（脚本删了断言过程就没了）。
    做法：把「验收结果 + 修改前后计数」写入 `evidence/<topic>/fix-stepNN.log`，
    带轮次编号。**过程（脚本）可删，结论（日志）必须留。**

11. **门禁的"跳过"分支必须显式区分「环境缺失」与「输入缺失」**：
    - 环境缺失（无 python）→ 可 `[skip]` 并打印原因
    - 输入缺失（无快照、无检查器文件）→ **必须 exit 1**，或提供显式 override 开关
    实例：G9 两轮——第一轮漏了 `$side`/`$csr` 预检，第二轮漏了快照全缺失的 `else [skip]`。

12. **消除问题 > 防护问题**（2026-10-23 第 16-17 轮沉淀）。
    实例：回归门禁的快照放在 `.tmp`（临时目录），清理工具会删。
    - 第一层修法（防护）：快照缺失时 `exit 1` —— **只是让问题暴露，门禁仍跑不了**
    - 第二层修法（消除）：把快照移入 `evidence/` 纳入版本控制，
      并删掉为"缺失"而设的 override 开关 —— **问题不存在了**
    **判断标准：如果修完之后还需要一个"例外开关/override/跳过分支"，说明还没修到根。**
    同理适用于所有"缺失即跳过"的门禁分支：
    - 环境缺失（无 python）→ 可 skip（不是本项目能保证的）
    - 输入缺失（无快照/无检查器）→ 必须 fail，且**优先考虑把输入纳入版本控制**

13. **扩展匹配范围时必须做反向验证**（第 16 轮 G10 教训）。
    把 `(?:^|;)` 扩成 `(?:^|;|:\s)` 覆盖了内联 if，但同时让
    `case X:` / `label:` / `{a: b}` / `int x:` / 三元 `?:` 全部变成"匹配"。
    **必须同时测两类输入**：①原本该匹配、现在仍匹配 ②**原本不该匹配、现在是否被误匹配**。
    只测第一类是"确认偏误"（只验证想验证的）。
    当前伪代码块 `case`=0/`label`=0/初始化=0 故不触发，但**这是"当前不触发"不是"不会触发"**，
    已在 `_classify_leaf` docstring 写明适用边界。

14. **"before" 状态必须改动前落盘，不能事后凭记忆补**。
    事后写的 before 段 = 回顾性叙述，不是当时的客观记录，**证明力弱于实测**。
    正确做法：每轮改动前先把当前计数/哈希/关键行为写入 `evidence/<topic>/fix-stepNN.before.log`，
    改动后写 `.after.log`，两者都是"当时的客观记录"。

15. **「引用统计」的两个假阳性来源**（2026-10-23 第 18 轮，两个都踩过）。
    (a) **子串匹配**：`stem in doc` 判 `iso.cpp` 是否被引用，`iso` 命中 `poisoned` 里的 `iso`。
        → 任何「是否包含/是否引用」判断必须用 `\b<完整标识符>\b`，禁止裸 `in`。
    (b) **自指污染（更隐蔽）**：在**审计报告**上统计引用是自指的。
        审计报告里有「未被引用的 22 个：`iso.cpp`, ...」这种否定性列举，
        也有「`iso.cpp` → 未引用」这种复核结论。
        词边界匹配 `iso.cpp` 得 11 次「引用」，**而这 11 次全都在说它没被引用**。
        → 引用统计只在**设计/实现文档**上做才有意义；审计文档的提及数必须单独列，
          且必须理解为「可能是否定性的」，不能当使用证据。
    **判断标准：统计「被引用」时，先问「这份文档会不会正好在讨论『没被引用』」。**

16. **统计「代码结构」必须先屏蔽非代码**（第 18 轮 G13）。
    直接在全文上正则计数，把 docstring 里提到的同一模式也算进去（报 9，实际代码 8）。
    后果不是门禁失败，而是**状态轨迹失真**——只改 docstring 措辞，指标就变，
    看起来像「少了一个锚点」。
    修法：`tokenize` 屏蔽 `#` 注释 + `ast` 屏蔽 docstring，**按精确字符区间屏蔽**
    （整行或屏蔽所有字符串 token 都会把代码本身也屏蔽掉），
    并**同时报告 docstring-only 计数**（当前 1）证明屏蔽生效、不是碰巧为 0。
    注意 `ast` 的 `col_offset` 是 UTF-8 字节偏移，`tokenize` 是字符偏移，必须换算。

17. **「可重现」必须实测，不能声明**（第 18 轮 Q4）。
    我说 `bcgr.txt`「可从官方文档重新获取」——这是未经验证的假设。
    实际做法：用 `docx2txt.py` 重新提取 `bcgr.docx`，
    两次 sha256 前 16 位一致（`ca703a9f3395801c`，1154865 B），
    并把提取脚本全文写进 `evidence/capabilities/bcgr-source.md`。
    **「可以从 X 重新生成」只有在真的重新生成过一次之后才是事实。**

18. **同名覆盖 = 没有轨迹**（第 18 轮 Q2）。
    `--step gate` 每次覆盖同一个 JSON，只有最新状态，与「记录轨迹」的初衷矛盾。
    修法：全量 JSON 覆盖写（只留最新）+ **追加式 JSONL 摘要**（永不覆盖）。
    JSONL 每行约 500B，天然是轨迹，diff 两行就能看出改了什么。
    **凡是「记录历史」的工具，都要检查「写入方式是否会覆盖历史」。**

19. **引用统计的三个假阳性来源**（2026-10-23 第 18-19 轮，三个都踩过）。
    (a) **子串匹配**：`stem in doc` 让 `iso` 命中 `poisoned`。→ `\b<完整名>\b`。
    (b) **自指污染**：在**审计报告**上统计引用是自指的。审计报告必然讨论
        「哪些没被引用」，于是那些文件名必然出现。实测含 consult-b 时
        **「引用 50 / 未引用 0」= 100% 全覆盖**，这本身就是污染的铁证。
        → 统计源只取**消费方文档**（design-a/design-b，用探针结论的），
          排除**元文档**（consult-b 讨论探针本身）。
          **判据不是文档类型，而是「该文档是否以这些名字为讨论对象」。**
    (c) **单词/文件名碰撞**：`probe.cpp` 的 stem 是 `probe`，
        `\bprobe\b` 命中 `schannel-probe.txt` 里的 probe 和英文单词 probe。
        实测 design-a 18 + design-b 4 = **22 次全是假阳性**，真 `probe.cpp` 只 2 次。
        → **口径必须要求扩展名**（`<stem>.cpp`），并**在产物里声明口径**。
    **通用原则：报任何数字必须同时报「用什么口径算的」，否则不可复核。**

20. **涉及表格/结构化数据时必须按列/字段切分，禁止整行关键字匹配**（第 19 轮）。
    实例：`"注释" in row` 统计 INDEX 的用途等级，报「注释=48/推定=0」——
    因为**每行都含「（无作者注释）」这句话**，全命中。
    改用按 `|` 切分取第 3 列后 4/44/2 正确。
    **这是本项目第 5 次「匹配方式错误」**（前四次：`'st' in cond`、
    `^\s*` vs `(?:^|;)`、`stem in doc`、`"注释" in row`）。
    **五次全是「用子串/整行匹配代替结构化解析」。**

21. **解析表格必须处理转义分隔符**（第 19 轮，第 6 次「工具产生错数」）。
    从 design-b 的探针表提取结论时，按 `|` 切分导致含 `` `1.2\|1.3` ``（转义管道）
    的行被切成 4 列、被 `len(cells)!=3` 跳过，`probe9`/`probe16` 静默消失。
    修法：`re.split(r'(?<!\\)\|', row)` 只按**未转义**管道切。
    同轮还有第 2 个提取器 bug：正则 `([A-Za-z0-9_]+\.cpp)` 漏了带路径的
    `.tmp/tlsprobe/probe5.cpp`，probe5 静默丢失。
    **教训：解析器的静默跳过比解析错误更危险——它不报错，只是少了一条。**
    必须让「跳过」打印出来（`SKIP (cells=%d)`）。

22. **「尺子变了」和「对象变了」必须分开报告**（第 19 轮）。
    `state_snapshot.py` 自己也在 WATCH 列表里（必要——记录轨迹是用哪个版本的
    测量工具生成的，与实验记录「仪器型号」同性质）。
    但它改自己时 sha 必变，`diff_state` 会报 CHANGED，**即使测量结果完全没变**。
    → `diff_state.py` 把工具变更单独归类并打「可比性降低」警告。
    **同时要区分「工具新增（before 无记录）」和「工具未变」——
    前者不能报 `unchanged`，那是假事实**（我第一版就报错了）。

23. **差分测试 > 硬编码期望值**（第 19 轮）。
    `verify_g13.py` 原版硬编码 `code == 8`。它测的是「是否等于我记住的 8」，
    不是「mask 是否正确」——文档合法新增第 9 个锚点时会误报失败。
    改为**与独立实现比对**：另写一个不 import `mask_noncode` 的扫描器
    （自己的 AST 遍历 + 自己的字符串/注释状态机），两者必须一致。
    **两个独立推导一致才是证据；等于一个常量不是。**
    注意 `ast` 的 `col_offset` 是 UTF-8 **字节**偏移，
    行起始表也必须按字节建，否则切片会在多字节字符中间断开（实测 UnicodeDecodeError）。

24. **「引用」有多种具体形式，只数文件全名会漏**（第 20 轮）。
    实测：10 个探针只以裸编号出现，逐个看上下文**全是真实证据引用**：
    `[BASH:probe10/probe12/probe17/probe27/probe36]`、`probe15.exe → "..."`、
    `consult-b probe41 → 0x1302`。
    → 引用判据必须接受**具体证据形式**：`<stem>.cpp` / `<stem>.exe` /
      `<stem>` 在 `[BASH:]`/`[READ:]` 标记内 / `consult-b <stem>`，
      **并逐文件列出理由**，否则数字不可复核。
    **教训：口径窄会漏真引用，口径宽会有假阳性。正解不是选一边，
    而是「多口径并列 + 逐条给理由」。**

25. **「总出现次数」≠「假阳性次数」**（第 20 轮，双方都算错过）。
    `\bprobe\b` 合计 22 次，其中真引用 2 次、假阳性 **20** 次。
    我报「22 次假阳性」是错的——**22 是总数，20 才是假阳性数**。
    **报差集时必须写「A - B = C」，不能只报 A。**

26. **驳回对方结论前必须先验证其前提**（第 20 轮）。

27. **差分测试的独立性取决于「信息源不同」，不是「写法不同」**（第 20 轮规则 H）。
    我写的两个实现都用 `ast.walk` + 同一套 `isinstance` 判断链，
    **写法不同但信息源相同**——`ast` 本身出错时两者同时错，差分发现不了。
    真正的独立：**换信息源**（`ast` 字节偏移 vs 纯文本三引号扫描）。
    加行号锚定（`:196` 是否在三引号块内，纯文本判断）作为第二信息源。

28. **状态判定必须三值：是 / 否 / 未知**（第 20 轮规则 I）。
    `diff_state` 第一版把「工具在 before 快照里不存在」报成 `unchanged`。
    **「没有记录」≠「记录了且没变」**。把「未知」当成「否」是这类 bug 的共同根源。
    与 G13（「docstring 里的锚点」≠「代码里的锚点」）是同一原则的两面。

29. **收敛判据（consult-b 第⑳步给出，用于终止工具打磨循环）**：

    - **判据 B（充分）**：新增缺陷的**最高级别**连续两轮下降

    - **判据 C（硬停）**：出现「为通过而改门禁判定」立即停止（作弊模式）

31. **实现期发现的设计文档缺陷 3 条（D1-D3）**：
    - **D1**：`SecPkgContext_ConnectionInfo::dwProtocol` 是 `SP_PROT_*` **位掩码**

      **design-a 没写这一条**，是实测发现的。
    - **D2**：`InitializeSecurityContext` 首次调用若输出缓冲是
      `cbBuffer=0, pvBuffer=nullptr`，返回 `SEC_E_INVALID_TOKEN (0x80090308)`。

    - **D3**：design-a 说 `overhead_actual` 可实测，但实测必须先加密一条记录，

32. **「预先切分记录」让 EXTRA 分支不可达**（第 22 轮 I2）。
    `Receive` 按记录头精确切出单条记录再 `DecryptMessage`，
    所以 `SECBUFFER_EXTRA` 恒为 0，算术定位那段是**死代码**。
    **死代码不是错误**（它是防御性契约），但**不能声称它被测试覆盖**——
    变异 M3 原来改那段，测试全绿，证明不可达。已改为 N4 长度上界的变异。
    **教训：变异测试「没翻红」时，先怀疑该代码不可达，再怀疑测试太弱。**

33. **终止闩锁的测试必须用「会产生不同状态」的输入**（第 22 轮 M4）。
    原测试喂一条**合法记录**，断言错误不变。但 TLS1.2 上下文本身已毒化，
    没有闩锁的实现也会返回同一个错误 → **假绿**。
    改为喂**非法记录类型**（`0xFF`），没有闩锁会返回 `kProtocolError`
    而不是原来的 `kDecryptFailed`，才能真正区分。
    **教训：验证「幂等」时，第二次输入必须能让「非幂等实现」产生不同结果。**

34. **构建脚本不能经 subprocess 传带引号的 vcvars 路径**（第 22 轮）。

37. **规范里的示例可能来自不同上下文，不能混用**（第 23 轮，D4）。
    `security-layer.md` §6.6.2 把 [MS-NLMP] **4.2.4.4** 的 checksum
    和 **4.2.3.4** 的密文放进同一张表。两个示例的会话密钥不同，
    这个组合**数学上不可能同时成立**。
    **症状**：按文档写测试，密文对但 checksum 永远不对，怎么调参数都不行。
    **排查方法**：反推所需 HMAC 输入（`target_cks XOR keystream`），
    看它与候选值是否匹配——比穷举参数快，且能区分「RC4 状态错」和「HMAC 输入错」。
    **最终以 PDF 原文为准**：4.2.3.4 明确写 `Cut key exchange key to 56 bits`，
    4.2.4.4 用 128 位（0x55×16），两者各自完全复现。

38. **自指测试无法检出缺陷**（第 23 轮，C1/C2 变异漏检）。
    我最初写 `CHECK(DecryptPubKeyAuth() == ClientToServerBindingHash(spk, nonce))`，
    **两边调用同一个函数**。把 magic 的 NUL 去掉、或把拼接顺序改错，
    **测试仍然全绿**——因为它只是在验证「函数等于它自己」。
    修法：把期望值写成**独立算出的十六进制常量**
    （用 Python `hashlib` 单独算一遍），这样才可能检出 magic/顺序/NUL 错误。
    **判据：期望值若来自被测代码本身，该断言无检出能力。**
    同轮另一例：MIC 测试原本断言「MIC 非零」，但零 MIC 和不发 MIC 无法区分，
    必须用三个消息独立重算 MIC 再比对。

39. **变异「没翻红」先查测试输入是否真的只违反了一条规则**（第 23 轮，T1）。
    `tsrequest_rejects_out_of_order_tags` 用的报文里 `[1]` 内容非法，
    所以即使删掉顺序检查，解码仍因内容无效而失败 → 变异漏检。
    修法：让**只有顺序错**、两个字段各自合法
    （`30 0a a2 03 04 01 cc a0 03 02 01 06`）。
    **同时补一条「合法升序必须能解」**，否则「拒绝乱序」和「拒绝一切」无法区分。

41. **注释声明 A、断言只验 B，是测试缺口的典型形态**（第 24 轮，S24）。

46. **「错误码丢失」有两种形态，修复点完全不同**（第 24 轮，S24-b）。
    形态一：**值被丢弃**。`tls_schannel.cpp:411` `ApplyControlToken(&ctx_, &desc);`
    裸调用，返回的 `0x80090302` 既没赋值也没比较，彻底消失。
    形态二：**值存在但被成功状态遮蔽**。`tls_schannel.cpp:429-431`

        closed_ = true;
        return MakeError(Status::kOk, st, "");     // st 进了 native_code
    }
    ```
    `0x00090312` 确实在 `native_code` 里，但调用方按 `Error::ok()`（`tls.h:62`
    只看 `status == kOk`）短路后根本不会去看。

47. **具体字节数不能跨上下文迁移，结构性结论可以**（第 24 轮，S25 探针）。

    - 我手写上下文实测 → **7 字节**（握手未完成，alert 是明文）
    - 甲的产品/已完成上下文 → **31 字节**（13 头 + 2 + 16 trailer）
    - 空 token + 已完成：裸上下文 **183 B**，产品 **201 B**
    **判据**：跨探针比对时，只能比对 record type / status / 布尔量这类**结构量**；

48. **「用例数 ≠ 覆盖」的三个实例（第 24 轮）**。

49. **「构造不出红证」永远先怀疑测试方法，不怀疑缺陷存在性**（第 24 轮，S24-b 订正）。
    我曾判定 S24-b（`tls_schannel.cpp:431` 把 `SEC_I_CONTINUE_NEEDED` 当成功）
    「红证不可构造」→ 不单列。**这个结论是错的**，原因是测试方法错：
    我只问「产品的正常路径能否触达那个分支」，答「不能」，就断言「不可测」。
    **正确的三种测试方法**（都实测出了红证）：
    1. **映射规则隔离测试**：把 `status → Status` 的映射抽成函数单独断言。
       `MapShutdownStatus(SEC_I_CONTINUE_NEEDED) != kOk` 今天失败，只修 `:431` 就通过。
    2. **产品行为自相矛盾即红证**：`status=kOk` 同时 `out` 是 201 字节重协商记录，
       两个事实互斥，不需要构造特殊输入。
    3. **跨平台差异即红证**：同一代码在 Linux 编不过、Windows 编得过，
       Windows 绿不证明没问题，只证明 **Windows 测试方法有盲区**。
    **判据：分支不可达 ≠ 规则正确。一个 `if` 的某个 arm 走不到，
    不代表写在那里的映射是对的。**
    **推论：遇到「测不出来」时，第一反应必须是「换个测试方法」，
    而不是「这个缺陷不成立」。**

50. **「改前就失败」不是「不属于本批」的理由**（第 24 轮，批 0 的 B1）。
    执行 AI 报告 Linux 全量构建有 3 个既有错误（`std::terminate` 缺 `<exception>`、
    两个未使用 helper），问是否修。我一度倾向「既有问题、转其他批次」。
    **按规则 50 这条也站不住**：它们在 Linux 上是真实缺陷（编译失败），
    在 Windows 上测不出来只是因为 **MSVC 的 `<string>` 传递引入 `<exception>`，
    而 libstdc++ 不会** —— 这是 Windows 测试方法的盲区。
    **判据：当批次的验收判据包含「某平台能构建」，该平台上的既有错误就属于本批范围，
    不管它是什么时候引入的。**

53. **修复「过时的行号引用」不能靠加 2**（第 24 轮，A20-1 的正确修法）。

54. **子串匹配的正向断言会接受错误值**（第 24 轮，A20-6 / B0-08）。

    - `"FAILED_COUNT=0 (tolerated 1 warning)"` 会匹配成功（应为失败）

?$`。
    **判据：凡「某行必须是某个精确值」的断言，必须用整行锚定，不能只查子串。**
    这与 B0-07（只看退出码）是同一族：**只信不够强的信号**。

55. **「可机器判定」不够，还必须「有区分力」**（第 24 轮，A20-1 判据）。

    不是「这条引用是否正确」。我沿用后报 86 处假阳性（其中 18 处是我已修好的新值）。
    **判据的两个必要条件**：
    ① 可机器判定（不用人工理解语义）；
    ② **有区分力**（必须存在让它返回 False 的输入，且该输入在现实中可能出现）。

56. **「原引用本身可能就错」——偏移量修复的前提不成立**（第 24 轮，A20-1）。

    **正确做法**：从语义重新定位（散文说什么 → 在新文件里找那个构造 → 写它的行号 + 锚点）。

59. **「记录性引用」必须保留旧值，不能一起修**（第 24 轮，A20-1 收尾）。

    | 位置 | 后果 |
    |---|---|
    | 散文叙述 | 读者困惑，可自行核对 |
    | **变异表 / 红证配方** | **红证假绿，缺陷被判定为已修复** |
    **判据：修复引用时按「读者会拿它做什么」排序，变异表/测试配方优先级最高。**

75. **写了「已由 X 验证」就必须重跑 X；改了被验证对象更要重跑**
    （第 24 轮，甲的 P1）。
    我在 `doc:3207` 插入 5 行修订声明 → `verify_sec19.py`（EXPECT 以 doc 行号作 key）
    全部失效（15/16 MISMATCH）→ **我却在 `doc:3211` 写「已由 verify_sec19.py

    **这是把假绿写进交付文档的正文，比代码里的假绿更危险**——读者不会再验证。
    **判据：文档里每出现一次「已由 X 验证」，X 必须在当前树上重跑通过；
    若改了 X 的输入（文档结构、源文件行号），必须先重跑再写这句话。**

76. **红证的注入点与判据的作用点必须是两个独立的东西**（第 24 轮，甲的红证 B）。
    我的红证 A：把文档里的 `:169` 改回 `:167` → 验证器报错 → 我判定「有区分力」。
    **甲指出：失败原因是 `anchor not found`，而锚点文本里内嵌了 `:169` 本身。**
    改回 `:167` 后锚点找不到，**根本没走到「源码第 169 行是否含该构造」这一步**。
    红证 A 只证明了「锚点查找」有效，**没证明「语义比对」有效**。
    甲的红证 B：**文档一字不改，只把源码 `:169` 改成 `consumed = in_size_other;`**
    → 报 `2 failed`。**这才是语义判据的证明。**
    **判据：设计红证前先问「这个注入会让判据的哪一部分执行？
    如果注入点同时改变了『找到目标』和『比对内容』，红证只能证明前者」。**

77. **「最小反例」必须真的最小，不能拿一个碰巧能复现的例子当通例**
    （第 24 轮，甲的 R-3 订正）。

    在 §6 里插 14 行 → 硬编码 exit=1、动态 exit=0。
    **判据：断言「X 会导致 Y 失效」时，必须构造出 Y 真正失效的最小输入；
    构造不出就说明「X 的规模不足以导致 Y」，结论要改成「X 达到某阈值时才会」。**
    这与规则 55（判据必须有区分力）同族：**区分力要靠能返回 False 的输入来证明，
    不是靠「改了一下它没坏」来证明。**

78. **「人工清单」永远追不上「全量」，必须换成「结构不变式」**（第 24 轮，乙的建议）。
    我的验证器是「32 条 pin 列表」。乙构造 4 个未被 pin 的探针，**2 个 BLIND**：

    正确的替代品是「对全部对象成立的结构不变式」**——例如「每条引用都必须带
    可 Select-String 的源码锚点」，它对 54 条全成立，不依赖「我想到了几条」。
    **两者都要有**：结构不变式管「不会静默漂移」，语义清单管「当前内容正确」。

79. **「看起来有锚点」和「锚点真能定位」是两件事**（第 24 轮，`doc:2473`）。
    `doc:2473` 写「锚点 `Error Handshake(..) .. closing brace`」——

    **判据：锚点必须是「在源文件中逐字存在的一段」**。验证方法：
    对每个锚点做 `grep -F`，0 命中即伪锚点。
    **这是「锚点化」这个动作本身可能造假**——写了「锚点」二字不等于有锚点。

80. **红证要针对「判据的每一部分」，不是「判据整体」**（第 24 轮，乙的批评）。
    我的红证 B：改**源码** `:169` → 验证器报错 → 我判定「语义检查有效」。

    会让锚点查找先失败）。
    **判据：一条判据有几个独立环节（找目标 / 比内容 / 查覆盖），红证就要有几个。
    只注入一种扰动，只能证明那一条路径。**
    本轮最终有了三个红证：改文档（红证 A）、改源码（红证 B）、剥锚点（锚点红证）。

81. **「知道规则」不等于「执行规则」，重复踩同一个坑说明缺的是动作而非知识**
    （第 24 轮，规则 58 第三次复发）。
    `$LASTEXITCODE` 在 `foreach` 循环里被覆盖 → 我得到 3 个假的 exit=1，

    规则 58 早已写下，仍然复发。
    **判据：同一错误复发 ≥2 次时，改的不是规则文本，而是默认动作**——
    把「逐个单独跑并存退出码」写进脚本模板，不靠临场记忆。

82. **「能搜到」与「能定位」是两件事——存在性判据必须升级为对应性判据**
    （第 24 轮，甲和乙独立发现）。
    我的锚点门禁：`if all(any(p in s for s in flat) for p in parts)`
    ——`flat` 是**整个文件**的每一行。**锚点在文件任意位置出现就通过。**
    于是「锚点 `return Fail(kProtocolError, st);`（在 `:293`）配引用 `:432`」被判为合法。
    | 判据类型 | 问的问题 | 能否发现错位 |
    |---|---|---|
    | 存在性 | 这段文字在文件里吗 | **不能** |
    | 对应性 | 这段文字在被引用的那一行吗 | **能** |
    **无锚点会红灯；错位锚点会假绿——后者更危险，因为文档因此声称「已验证」。**
    **判据：任何「锚点/引用/映射」类检查，判据必须是「两者在同一位置」，
    不能是「两者都存在」。** 这是规则 68（多引用行）的一般化。

83. **宽容性回退必须与被修复的缺陷在同一维度上正交**（第 24 轮，v7 的致命错误）。
    v6 正确（只查被引行）。v7 我加了「裸 `:NNN` 可能解析到错误文件，所以尝试所有文件」。
    **但这条回退让「锚点在 `:293`」满足了「引用 `:432`」——同一文件、不同行。**
    红证立刻抓到 P1/P2 BLIND。
    **判据：「文件判错」和「行判错」是两个维度。用「换文件重试」修「行错」是维度错配，
    它会把被修复的缺陷重新放回来。**

84. **同一个错误修了一处，必须主动搜同类**（第 24 轮，伪锚点）。
    `doc:2473` 的锚点 `Error Handshake(..) .. closing brace` 是散文、源码里没有，我修了。
    **但 `doc:1798` 和 `doc:2050` 有一模一样的伪锚点，我没搜。**
    是「对应性判据」上线后才抓出来。
    **判据：修一处缺陷后，立刻用同一字符串/同一模式全文搜一遍。
    「修了一个」不等于「修了这类」。** 这是规则 15（C9 同型排查）的文档版。

85. **子进程编码：父进程指定 encoding 不够，必须同时约束子进程的输出编码**
    （第 24 轮，乙的发现）。
    `citations_redtest.py` 在非 ps1 环境崩溃：`p.stdout=None` → `AttributeError`。
    我原以为父进程 `encoding='utf-8'` 就够。**不够。**
    子进程无 `PYTHONIOENCODING` 时按 locale(GBK) 输出，父进程按 utf-8 解码失败。
    在 ps1 里不崩，是因为 `verify.ps1` 设了 `$env:PYTHONIOENCODING="utf-8"` 并被继承
    ——**这掩盖了缺陷，让它在别的环境才暴露。**
    **判据：`subprocess.run(..., encoding=...)` 必须同时传
    `env=dict(os.environ, PYTHONIOENCODING='utf-8')`。**
    并且：**「在门禁里能跑」不等于「能独立跑」**，红证脚本必须能独立复跑。

86. **「锚点在区间内」不能证明区间边界正确**（第 24 轮，甲的 15 处里 6 处是区间）。
    `t:489-507` 引用 `FinishHandshake`，该函数在 `cur[491]`——**落在 489-507 内**，
    所以「锚点在区间内」判据放行。但 `cur[489]` 是空行、`cur[507]` 不是函数尾
    （`cur[509]` 才是 `}`）。**区间边界错了 2 行，判据看不见。**
    **判据：区间引用的锚点必须钉住边界**——首片段在 `cur[A]`，末片段在 `cur[B]`。
    「区间内存在」是存在性判据的区间版本，同样没有区分力。

87. **唯一性是「能否作证」的前提，不是锦上添花**（第 24 轮，乙的 A6 探针）。
    `closed_ = true;` 在 `:304` 和 `:432` 都存在。锚点用这行、引用写 `:432` → 通过；
    把引用改成 `:304`、锚点不动 → **仍然通过**。**引用号写错，门禁照样绿。**
    **判据：锚点的命中行集合必须 ⊆ 被引区间。若同一文本在别处也出现，
    它就无法区分那些行，因此无法为这一行作证。**
    **例外只有一个**：锚点带 `(in Func)` 消歧，且该函数确实包住被引行。
    **但这个例外不能替代「锚点文本必须在被引行」**——红证 A1/A2 证明，
    只看函数会让「锚点取自相邻行」通过。

88. **「豁免理由」必须实算覆盖率，不能凭印象**（第 24 轮，乙的 §19 缺口）。

89. **行数基线也是引用，同样会过期，且没有冒号所以逃过所有正则**

90. **改正则后必须立刻重跑全套验证**（第 24 轮，我的失误）。

92. **归因必须核实，别人否认的发现不能记在他名下**（第 25 轮）。

93. **同型错误的成组排查：修一处前先搜同类**（第 25 轮，S22 有 6 处）。

94. **改锚点前必须确认目标行的真实文本**（第 25 轮，我差点引入新缺陷）。

95. **「改错地方也能让测试变绿」是最危险的引用错误**（第 25 轮，`:433` vs `:435`）。

96. **审计报告章节里的旧值是证据，不是缺陷**（第 25 轮）。

97. **成组错误要扫「同一行的旁证」，不只是「同一构造的修复点」**（第 26 轮）。

98. **「锚点自洽」不等于「锚点符合散文」，但有些语义是源码侧可查的**（第 26 轮，X1）。

    只看「引用自身声称了什么」。声称自己是完整块 → 就必须是函数。**

99. **探针必须有自校验（替换是否真的落地）**（第 26 轮，乙自己踩了）。

100. **别人报的例子可能有技术错误，但结论可能仍对——两者必须分开核**（第 26 轮）。

101. **白名单必然漏，黑名单才封闭**（第 27 轮，甲乙同报 SIG 假阳性）。

    **本文件 24 个真函数，它漏 5 个**：析构（无返回类型）、`uint32_t`、
    `static uint16_t`、`PCCERT_CONTEXT`、`static Error`。
    **返回类型是开放集合**（任何用户类型/typedef/`static` 组合），白名单永远漏下一个。
    **改成黑名单**：能开块且不是函数的构造是封闭的十来个关键字
    （`if/else/for/while/do/switch/case/default/try/catch/return/`
    `namespace/struct/class/enum/union/typedef/using`）。
    **判据：判「是不是 X」时，枚举「不是 X 的特征」比枚举「X 的特征」稳。
    后者随代码增长而失效，前者只随语言演进变化。**

102. **测试必须同时守假阴性和假阳性**（第 27 轮）。
    我的 `anchors_redtest.py` 前 13 个探针**全是「错误引用必须失败」**。
    **没有一条守「正确引用必须通过」。** 于是 SIG 白名单误杀 5 个真函数时，探针全绿。
    **判据：一个判据的探针集必须成对——「该拒的拒了」+「该收的收了」。
    缺后者，误杀永远不会被发现，而误杀会让维护者不信门禁、或去改正确的引用。**

103. **短别名是显式文件归属，不能参与「向左找文件名」的推断**（第 27 轮）。
    `doc:2443` 同一行先引 `tls.h:148-150`、再引 `t:246`。

    **`t:` 是 `tls_schannel.cpp` 的显式别名，语义上等同于写了文件名。**
    修法：`if m.group(0).startswith('`t:'): return 'tls_schannel.cpp'`。
    **判据：别名优先于上下文推断。凡是「显式简写」，都必须先于「就近推断」被检查。**

104. **二分普查（分类器认/不认）会掩盖「不认但正确」这一类**（第 27 轮，我的失误）。
    我用「SIG 匹配 / 不匹配」做普查，把 70 个不匹配**统统归为「内层块」**。

    **判据：验证分类器必须独立定义正类再比对，禁止拿分类器自己的判定当基准。
    否则普查只是在复述分类器的行为，永远发现不了它的错。**

105. **两条判据偶然互补 ≠ 设计正确——每条必须独立成立**（第 28 轮）。
    v12 的黑名单对 `} else if (...) {` 判为「是函数」（`INNER_BLOCK` 因行首 `}` 不匹配，
    该行又有 `(`）。**但 `brace_balanced` 恰好拒绝它**（depth != 1），所以没出事。
    **这不能算门禁正确，只能算这次恰好没出事。**
    若 A 错、B 对且 B 恰好覆盖 A 的错：A 的错误仍在（换个 B 覆盖不到的输入就暴露），
    后来者还会误以为 A 是对的、据以推理。
    **判据：修 A，不靠 B 兜底。「这次没出事」不是正确性证据。**

106. **审计工具的「独立定义」也可能错，必须自查**（第 28 轮）。
    我写全量普查时，oracle 第一版报了 14 个 mismatch，

    **判据：审计工具的 oracle 必须先用「已知正确的样本」自测。
    报出的 mismatch 要先怀疑 oracle，再怀疑被测对象。**

107. **未执行批次的预检只能证明「缺陷仍在 / 测试名未占用 / 基线可测」，不能证明变异点精确**（第 29 轮）。
    我写 `batch1_preflight.py` 连错两次：
    - 第一次检查 `std::clamp` / 空公钥检查是否存在 → 报 2 条 MISS。
      **错**：红证表是「变异（改回修复前）」，这两样是**修复后**形态。
    - 第二次检查 5 个测试名是否存在 → 报 5 条 MISSING。
      **错**：§19.1.3 强制 TDD，测试是执行者**要新写**的。
    **判据：先确认批次状态（已执行/未执行），再决定预检问什么问题。**
    已执行批次 → 「锚点是否还定位到目标行」；
    未执行批次 → 「缺陷是否仍在 + 新测试名是否未被占用 + 基线是否可测」。
    变异点精确性（Q4）修复前**不可验**，必须修复后重跑预检、看 S5b/S6 翻为 PRESENT，

108. **校验别人的结论前，先确认自己用的是同一个模型**（第 30 轮）。

    拿不同的数据形态去否决别人，会把正确结论判成造假。**

109. **新加守卫必须验证「可达性」——它在真实数据上改变过判定吗**（第 30 轮）。
    我在 `starts_a_function` 里加 `CLOSING_PREFIX`（`}` 前缀拒绝），并且**当时就在注释里写了**
    「两条规则偶然互补不是设计」。然后乙证明：本文件中「以 `}` 开头且能自行配平」的行 **= 0 条**，

    `brace_balanced` 先返回 False 就短路——守卫连被调用的机会都没有。
    **判据：加守卫后必须做两件事——
    (1) 可达性：在本数据上找一个它真的翻转判定的输入；
    (2) 区分性：删掉守卫，该探针必须由 exit=1 翻为 exit=0。

110. **任何会被反复启动的探针 exe，必须内建崩溃静默，否则一个断言能锁死整台机器**（第 31 轮）。
    审计探针是 MSVC `/MDd` 构建，`_ITERATOR_DEBUG_LEVEL=2` 生效。迭代器误用触发 CRT 断言，
    默认报告模式是 `_CRTDBG_MODE_WNDW` —— **模态框**。子代理在 `foreach` 里循环启动它，
    每轮弹一个框，循环永远不前进，桌面被刷满。**两次了。**
    **必须同时做两半**：
    - 进程内：`silent_crash.h` —— `_CrtSetReportHookW2` 捕获断言文本后 `_exit(4)`；
      `SetUnhandledExceptionFilter` 写 minidump 后 `_exit(5)`；`SetErrorMode(SEM_NOGPFAULTERRORBOX)`。
    - 进程外：`run_probe.ps1` —— 看门狗超时 + `taskkill /T`，覆盖「编译时还没接保护」的旧 exe。
    **强制手段**：探针只能用 `build_probe_safe.bat` 构建，它用 `/FI silent_crash_auto.h`
    把安装代码注入**每个 TU**（静态初始化里调用 `Install`），
    **探针源码无法意外逃逸**——已验证：完全不写保护的源码，仍然 0 弹窗。
    **判据：一次性脚本/探针也要做故障隔离。凡是「会被循环启动」的东西，
    失败必须变成退出码，不能变成 UI。**

111. **`-match 'probe_'` 会把执行这条命令的 PowerShell 自己匹配进去**（第 31 轮）。

112. **验证门禁必须做「负向自测」——否则你不知道它是绿的还是死的**（第 33 轮）。
    乙指出 `batch1_preflight.py` 三条正则**在修复后会误报 BAD**：

    **判据：任何「检查某段代码是否存在/消失」的正则，必须同时用修复前和修复后的样本各测一次。

113. **先做负向自测，再接进门禁**（第 33 轮）。

114. **裁决前必须查「下游映射」——枚举注释不是语义，实际用法才是**（第 35 轮）。

115. **「靠 message 区分」必须有仓库契约支撑，否则是空想**（第 35 轮）。

116. **新增枚举值前必须验证「无 switch 穷举 / 无数值比较」**（第 35 轮）。

117. **断言某个门禁「会误报」之前，必须先读它的实现**（第 35 轮）。
    我担心 `random.cpp` 用单文件 `#ifdef _WIN32` 会触发 Linux 门禁，理由写成

    **它扫的是构建日志，不是源码。** `#ifdef` 分支在 Linux 上不编译、不进日志，
    根本不会触发。结论从「必须分文件」降级为「分文件只是更清晰」。
    **判据：说「某个检查会误报」之前，先打开它读一遍。凭名字猜实现，
    会把「风格偏好」说成「硬约束」，误导执行者。**

118. **只打印结论而不设退出码的脚本，是一道永远无法失败的门禁**（第 36 轮）。
    `batch1_preflight.py` / `batch2_preflight.py` 都只 `print('RESULT: BLOCKED')`，
    没有 `sys.exit` / `raise SystemExit` / `assert`。而 `verify.ps1:331-332` 靠 `$LASTEXITCODE` 判定。
    **强制失败实测**：输出 `BLOCKED`，**退出码 = 0** —— 两道门禁零保护。
    审计乙报出，我复现后修：`raise SystemExit(0 if ok else 1)`，复验强制失败 exit=1。
    **判据：任何被 `$LASTEXITCODE` / `$?` 调用的脚本，必须让退出码承载结论。
    「打印了 BLOCKED」不是失败，退出码非零才是失败。**

119. **正则门禁必须剥注释，否则「把 bug 写进注释」就能让门禁变绿**（第 36 轮）。
    N-B1 的门禁 `want=True`（缺陷应 PRESENT）。修复后若写一句很自然的解释性注释：

    ```
    正则 MATCH → 报 PRESENT/OK → **门禁因为文档记录了 bug 而通过**。
    修法不是改这一条正则，而是让 `present()` 对所有行统一 `_code_only()`（剥 `//` 与 `/*...*/`）。
    **判据：凡是「检查某段代码存在/不存在」的正则门禁，必须先剥注释。
    否则注释既是假阳性源，也是假阴性源。**

120. **同名同值不等于可复用**（第 36 轮）。

121. **没有回归用例的约束等于没有约束**（第 36 轮）。

    否则它只是文档里的一句话。**

122. **复验别人的技术断言，必须验证「前提事实」，不能只验证推理过程**（第 37 轮）。
    审计甲断言「`-std=c++20` → `__STRICT_ANSI__` → glibc 隐藏 `getrandom` → Linux 门禁必红」。
    我逐条核了他的推理链：`CMAKE_CXX_EXTENSIONS OFF` 成立、`__STRICT_ANSI__` 被定义成立、
    `rtsc_credssp_sm_tests` 无 WIN32 守卫成立 —— **每一步都成立，我就签了「复验通过」**。
    **但起点事实是错的**：g++ 在 Linux 上**无条件预定义 `_GNU_SOURCE`**，
    glibc 见到它就置 `_DEFAULT_SOURCE=1`，`__STRICT_ANSI__` 分支根本不被求值。
    实测 `g++ -std=c++20` 下 `getrandom` 完全可用（`ok done=8`）。
    **判据：推理链自洽 ≠ 结论正确。必须验证最上游的那个事实假设。
    核「A→B→C」时，先核 A 是不是真的。**

123. **跨平台/工具链断言必须先跑再报，强措辞要有实测支撑**（第 37 轮，审计甲自我总结）。
    甲用「**必红**」这种强措辞给出 Linux 门禁结论，但当时没有 Linux 实跑。
    他后来补了三份 WSL 实测证据，并把结论从「必红」降为「按实测写法直接绿」。
    **判据：凡涉及编译器/glibc/CMake/链接器的断言，必须给出可复现的命令 + 输出。
    没有实测就说「必红」，会把执行者引向错误方向（比如去加不必要的宏、
    或在自己代码里找不存在的问题）。**

124. **真正的静默缺陷是「能编译但行为错」，编译错误反而安全**（第 37 轮）。
    甲的 `_DEFAULT_SOURCE` 论点是「编译失败」——**这种错误一眼可见，不可怕**。
    真正危险的是 `EINTR` 缺失：`if (r < 0) return false;` **编译通过**，
    但任意信号打断 `getrandom` 就误报 CSPRNG 失败 → `Status::kInternal`
    → **难以复现的间歇性握手失败**。
    **判据：评估风险时，把「能编译但偶发行为错」排在「编译失败」之前。
    前者会活到生产环境，后者在 CI 就被拦住。**

125. **验证脚本必须先在「已知坏样本」上红、在「已知好样本」上绿**（第 38 轮，审计甲）。
    甲写 30 项交付检查时，加了一个「正向对照」——用参考实现跑同一组判定。
    结果抓出他自己 4 个误判：
    - **D5 假绿**：只查 `nonce_.size() != kNonceSize` **存在**，没查**顺序**。
      旧代码的守卫在切片**之后**——那正是缺陷本身。**「存在」≠「正确」。**
    - **D4 假绿**：`DeriveSigningKey(..., true)` 在 `c:384` 确实存在，但那是
      **OpenReceive（收方向）**，他当成了发送方向已修。**同名不同处，必须锚定函数上下文。**
    - **D4 假红**：修完上条后正则过宽，把 `SealSend` 里**正确**的 `signing_key_` 也判成错。
    - **D6 假红**：`find('error_code')` 命中了构造器附近，不是 `req.has_error_code` 分支。
    **他的话：「没有正向对照，30 项里至少 2 项会把错判成对（D5、D4）。这比不做检查更危险。」**
    **判据：新写的检查必须先在一个「它应当拒绝」的样本上观察它拒绝，
    再在一个「它应当接受」的样本上观察它接受。只跑真实目标，你不知道它是绿的还是死的。**

126. **改代码会让文档引用漂移，改完必须跑引用门禁**（第 38 轮）。
    批 1 改写 `credssp.cpp` 后，行号整体下移。`security-integration.audit-a.md` 的
    红证配方表仍写 `c:46` / `:93-94` / `:357-360`，而实际位置变成 `c:52` / `c:127-129` / `c:423-443`。
    `verify_citations.py` 立刻报 3 FAILED（它比对的是**当前**文件内容）。
    **判据：任何改变源文件行数的改动，都要重跑引用/锚点门禁。
    「文档说的」和「代码做的」分叉时，门禁是唯一能发现的地方。**

127. **变异测试必须独占工作树——并行变异会让 verify 结果不可信**（第 39 轮）。
    批 1 执行 AI 验证红证时，我也在跑 8 条变异脚本，两边同时改写同一个 `credssp.cpp`。
    结果：执行 AI 看到 `-DocCite` 报 `server_echo_version_does_not_downgrade` 红（我的变异版被构建进去）；
    我自己看到 `sm_tests 1 failing` + `semantic_redtest.py exit=1`（同一原因）。**重跑即绿。**
    **判据：同一时间只允许一个代理改写 `src/`。
    变异前记录 SHA256，变异后验证恢复；观察到的失败必须重跑确认可复现才当真实缺陷。
    要并行就用独立影子树，不要共享源码目录。**

128. **测试「只比一个量」会在相邻修复后失效**（第 39 轮，执行 AI 自己发现）。
    `two_constructions_have_different_nonces` 原本只比 `ExportedSessionKeyForTest()`。
    N-B1 修复后 exported key 已独立于 nonce，**于是 nonce 恒定时两个 key 仍然不同，测试保持绿**。
    执行 AI 首轮 S1 变异是 **STILL-GREEN**，他补强为同时断言 `req.client_nonce`
    （32 字节 / 非全零 / 两两不同）后才 RED。
    **判据：一条测试若断言的是「A 和 B 不同」，当 A 变成独立随机源后，
    这条测试就不再约束 B。修完一个缺陷，必须重跑相邻缺陷的红证。**

129. **变异脚本不要用常量条件短路（`if (false && ...)`），要删除代码**（第 41 轮，审计甲）。
    甲做红证变异时写 `if (false && ...)`，MSVC 报 **C4127**（常量条件），
    在 `/W4 /WX` 下是**编译错误** → 3 条变异 BUILD-FAIL，不是 RED。
    改用「删除修复代码，还原修复前行为」后才 8/8 通过。
    我自己用 `if (false) {` 没撞上，是因为我**整体替换**而不是 `&&` 拼接——运气，不是设计。
    **判据：变异要还原「修复前的代码形态」，不是「让条件恒假」。
    后者在 /WX 下可能编译不过，而且看起来像作弊。**

130. **不要凭「文本前缀一致」断定事故归属**（第 41 轮，我自己的错）。
    执行 AI 报告看到变异文本 `/* no write-back */`；我脚本正是这个；
    甲**最终版**影子脚本用 `/* mutation: no write-back */`。我据此认领为「我的责任」。
    **但甲第一版（已被覆盖）用的什么文本无法还原**，而且甲也承认同期改过真实树。
    只凭前缀一致就断定归属，忽略了「对方也承认」这个反证。
    **判据：事故归属需要「唯一性证据」——能排除其他所有可能肇事者。
    只有「我的格式匹配」不够，必须证明「别人的格式不匹配」。做不到就写「双方均可能」。**

131. **红证配方必须写明「预期失败的用例是否存在、断言是否够强」**（第 42 轮）。
    批 2 的 §19.3.3 表列了 8 条变异和「哪条用例该红」，但实测：
    **6 条用例根本不存在**（`shutdown_reports_continue_needed_as_failure` 等），
    另 1 条（`shutdown_is_idempotent`）**断言只有 `!first.empty()`，没有 `first[0] == 21`**，
    所以「把 token 改回空」这条变异**仍会绿**。
    **判据：一张红证表至少要能回答三件事——
    (1) 变异什么；(2) 哪条用例该红；(3) **那条用例现在存在吗、它断言的东西真的会被这个变异改变吗**。
    缺 (3) 的表是不可执行的，执行者照抄会撞墙。**
    批 1 之所以顺利，是执行 AI 自己补强了 S1 的断言（memory 128）；不能指望每批都有这种运气。

132. **批 2 是修复批，锚点指向「修复前」的缺陷代码，不是修复后**（第 42 轮）。
    我一度以为 `c:411 SecBuffer token{0, SECBUFFER_TOKEN, nullptr};` 是「已修好的样子」，
    实际它**就是缺陷本身**（空 token 意味着 SChannel 收不到 SCHANNEL_SHUTDOWN）。
    表里「变异 = 恢复成空 token」的方向是：批 2 先把它改成
    `SecBuffer token{sizeof(type), SECBUFFER_TOKEN, &type};`，红证时再改回空。
    **判据：拿到一张「缺陷表 + 变异表」时，先确认当前代码处于缺陷态还是修复态。
    两者的变异方向相反，搞反了会得出「这条已经修好了」的错误结论。**

133. **每批收尾要问「哪些代码被动了」，不是「哪些缺陷修了」**（第 43 轮，审计乙发现）。
    批 1 的红证表只覆盖被点名要修的 8 条，全部真红。但我独立实测发现
    **另外三处代码改动零回归保护**：删除 D5 nonce 尺寸守卫、`seq != recv_seq_` 校验、
    sealed-field version 校验，测试**仍然 23/205/0 全绿**。
    根因：`FixedNonce()` 恒 32 字节、seq 恒 0、version 恒 1，三条守卫永不触发。
    **判据：红证表回答「我修的那几条真的被抓住了吗」，
    但答不了「我顺手改的那些行有没有人管」。
    收尾必须逐行过一遍本批 diff，每一行问：这行被删掉/改错，哪条用例会红？答不出就是裸奔。**
    对照组证明方法有效：同一次实验里 S5 变异 → 2 红、MAC 变异 → 1 红。

134. **`if (false)` 做变异在 `/WX` 下会因「变量未使用」再次翻车（C4189）**（第 43 轮）。
    memory 129 记了 C4127（常量条件），这次实测 C4189：把 `if (seq != recv_seq_)` 改成
    `if (false)` 后，`seq` 变成「初始化但不引用」→ `/W4 /WX` 编译失败，变异 BUILD-FAIL。
    **正确做法：整块删除**（含 `plaintext.clear()` 和 `return`），必要时加 `(void)seq;`。
    这条两次被实战验证（甲一次、我一次），不是理论风险。

135. **崩溃型缺陷的红证形态是「进程崩溃」，不是「用例失败」——必须看退出码**（第 44 轮）。
    删掉 D5 nonce 守卫后，`short_nonce_is_rejected_not_crashed` 不是报 FAIL，
    而是**整个进程崩掉**：`exit=3221226505`（`0xC0000409` STATUS_STACK_BUFFER_OVERRUN），
    stderr 是 `vector(122): Assertion failed: cannot seek vector iterator after end`。
    我的第一版红证脚本只解析输出里的 `N tests, M checks, K failing` 摘要行，
    得到 `NO SUMMARY`，差点误判成「脚本坏了」。**单独查 exit code 才发现是崩溃。**
    **判据：红证脚本必须同时捕获 (1) 进程退出码 (2) 摘要行 (3) stderr。
    只解析摘要行，遇到崩溃型缺陷会得到「无摘要」而不是「红」，
    于是你会去修脚本，而不是意识到「这条检查在防崩溃」。**

136. **`0xC0000409` 在本项目里出现两次，都是「守卫位置/存在性」问题**（第 44 轮）。
    第一次（批 1 审计）：S18 空公钥守卫若放在 `Start` 会崩，必须放 `BuildStep3` 入口。
    第二次（批 1 补测）：D5 nonce 尺寸守卫**根本不能删**——删掉后 24 字节 nonce 在
    `BuildStep3` 里被切片，直接 vector 越界。
    **判据：本项目里凡是「检查一个缓冲区长度」的守卫，都要问「删掉它会不会越界」，
    而不只是「删掉它会不会让错误晚点被发现」。
    前者是内存安全，后者只是错误码整洁——优先级完全不同。**

137. **读缺陷表要区分三种状态描述，我混淆过 (2) 和 (3)**（第 45 轮，我自己的错）。
    §19.3.3 的 S24-a 行写「预期失败 `shutdown_is_idempotent`（`first[0] == 21`，实际得到 22）」。
    我 grep `first[0]` 零命中，就推断「这条预期失败描述有问题」。
    **错了。** 表说的是「修复后应该是 21，当前得到 22」——这是**目标**，不是**已有断言**。
    实测 `evidence/tls/s24-measurement.md` 确认：缺陷态 `record type = 22 (Handshake) out=201`，
    修复态 `record: type=21 (Alert) total=31`。**表的描述是准确的。**
    **判据：缺陷表里每行都可能在说三件不同的事——
    (1) 当前代码行为（实测事实）(2) 修复后应有行为（目标）(3) 已有测试断言（覆盖）。
    看到「某断言不存在」时，先问它在说哪一件，不要直接判表错。**

138. **「现象证据」和「机理推论」是两份材料，缺一不可**（第 45 轮，审计甲自己总结的教训）。
    甲说 S10「可能不可构造」，因为他只读了 `tls_schannel.cpp:166-169` 的注释（现象层）。
    但 `s10-measurement.md` 的推论（「密文仍然可解，只是调用方手里已经没有了」）
    才证明**修复可行**，从而证明红证可构造。
    反过来，我查到了 `probe_s10.out.txt` 的 M1/M2 输出（现象），但没读 measurement 的推论，
    所以我只能说「现象存在」，说不出「为什么能修」。
    **判据：查一个缺陷是否可修，需要两样东西——
    探针输出（它现在怎么坏） + 推论文档（为什么修得了）。
    只有前者，你不知道能不能修；只有后者，你不知道是不是真的坏。**

139. **写文档脚本时 Windows 路径会被转义序列吃掉，必须用 `r''` 并事后扫控制字符**（第 45 轮，我的错）。
    我用 Python 往 `security-integration.audit-a.md` 写 PowerShell 片段，路径
    `F:\rtsc\.tmp\build_tls.bat` 在普通字符串里变成 `F:<CR>tsc<TAB>.tmp<BS>uild_tls.bat`。
    结果文档里混入 **2 个 0x08（BS）、1 个 0x0b（VT）、1 个 0x09（TAB）**，
    肉眼看不出，但执行 AI 照抄必然失败。审计甲逐字节扫出来才发现。
    **判据：凡是用脚本写含 Windows 路径的文档，字符串必须 `r'...'` 或 `\\`，
    写完后必须扫 `0x08/0x09/0x0b/0x0c/0x0d` 与 U+FFFD。**
    更糟的连锁错误：我修复时**插入新块却没删旧块**，导致 `BATCH2 BUILD FAILED` 出现两次，
    并把「通用前置」块（本应只有 1 行 TEMP 设置）覆盖成批 2 专属门槛，
    会让批 0/批 3/批 4 全跑错门槛。**修文档要「替换」不要「插入」。**

140. **同一现象的两份探针可能测的是不同场景，不能取其一就下结论**（第 45 轮，我差点又错）。
    `probe_u4.out.txt`（明文裸 alert）→ `native_code=0x80090318`，「description 不可读」。
    `probe_u4e.out.txt`（SChannel 加密的 close_notify）→ `native_code=0x00090317`，
    `plaintext` 是 31 字节整条 record 的包装。
    **两者都对，但测的是不同东西。** 产品 `c:301-305` 走的是后者（`SEC_I_CONTEXT_EXPIRED` → `kClosed`）。
    我一度按前者把 S23 的预期值写成 `0x80090318`——**错**。
    **判据：一个缺陷有多份探针证据时，先确定「产品实际走哪条路径」，
    再选对应的那份探针。选错探针 = 预期值写错 = 红证永远不成立。**

141. **「改注释」型缺陷，行为用例对它没有判别力**（第 45 轮，S23）。
    S23 是 `tls.h:42` 的注释撒谎（承诺 `native_code = alert description`），
    产品代码行为**本来就对**。所以任何行为型用例都无法让「注释改回去」这个变异变红。
    **判据：缺陷分两类——「代码错」用行为用例锁，「文档/注释错」必须用文档断言锁。
    两类都要，且各锁一个方向：**
    - 文档断言锁「注释不许撒谎」
    - 行为用例锁「代码不许按错误注释去改」（如把 `plain[0]` 当 description）

142. **注释修完仍可能撒谎——「说它会发生」和「说它不会发生」是两个不同的谎**（第 46 轮，审计甲发现）。
    S23 的第一版修复（U-N10 原文）把
    `native_code = alert description` 改成 `Backend surfaced a fatal alert`。
    听起来对了，但实测 **`kPeerAlert` 在全仓从未被产出**：
    `tls.h:42` 定义、`tls.h:68` 的 `terminal()` 判断、`test_tls.cpp:249` 的枚举列举，
    **`src/` 零命中**。SChannel 收到 close_notify → `kClosed`；收到加密 alert → `kProtocolError`。
    所以 U-N10 版让读者以为它某种情况下会产生——**换了个说法的同类错误**。
    **判据：改「能力承诺」类注释时，必须同时写清三件事——
    (1) 这个状态是给谁预留的；(2) **当前有没有任何后端产出它**；(3) 为什么拿不到那些细节。
    只说「做不到 X」不够，必须说「今天没有任何路径产出它」，否则读者仍会以为有路径。**

143. **文档断言必须「正向三要素 + 负向排除」双断言，纯负向很脆**（第 46 轮，审计甲）。
    我原设计只查 `kPeerAlert` 行附近**不含** `native_code = alert description`。
    甲指出：有人写 `native_code != alert description` 或 `native_code is not the alert
    description`，字面检查就失效——**改个说法就绕过门禁**。
    正确做法：
    ```python
    must_contain    = ['kpeeralert', 'cannot', 'no backend produces']
    must_not_contain = ['native_code = alert description']
    ```
    实测三版注释判别力：旧文案红、U-N10 版红（缺第三要素）、甲版绿。
    **判据：门禁的负向检查只能证明「旧错误没了」，不能证明「新表述是对的」。
    必须同时要求正向关键词存在，否则改个说法就绕过。**

144. **「哪个输入会崩」必须 grep 出真实表达式，不能凭印象推区间**（第 48 轮，我错了）。
    我给执行 AI 写「24 是唯一会触发越界切片的（因为切片在 `[8..24)`）」。
    **代码里根本没有 `[8..24)` 切片**——全文件只有一处：
    `c:215 in.client_challenge.assign(nonce_.begin(), nonce_.begin() + 8);`
    **8 字节，起点 0。** 所以危险尺寸是 `n < 8`，与 24 无关。
    乙在 `_GLIBCXX_DEBUG` 下实测：`n=0,1,4,7` abort；`n=8,24,32` 正常。
    **判据：说「哪个值会崩」之前先 grep 出切片/索引表达式。
    凭印象重构代码 → 推出错误的危险值 → 执行 AI 照着写错测试矩阵。**

145. **验证影子树必须在真实树每次改动后重新复制**（第 48 轮，乙发现）。
    我报告 `26/258` 并声称「删 D5 → 0xC0000409」，但我的影子树里
    `test_credssp_sm.cpp` 是 **1005 行**，真实树已 **1042 行**——
    执行 AI 后来把边界集从 `{0,24,31,33}` 扩到 `{0,1,8,16,24,31,33,64}` 并加了 version 4 循环。
    **旧版结论对旧代码成立、对新代码不成立，但它看起来是实测的——这比没结论更危险。**
    而且 version 4 循环是关键：只测 version 6 时，删掉 D5 早期守卫仍会被
    `c:275` 的旧检查拦住，测试保持绿。
    **判据：影子树的 SHA 必须和真实树比对并写进报告。
    「我实测过」这句话，只有在影子树 == 真实树时才成立。**

146. **工具写对了不等于工具生效——必须验证「接线」和「同步」**（第 48 轮，审计甲发现两处）。
    - 缺口 1：`batch2_gate.py` 写好了、自测通过，但 **`verify.ps1` 里零引用**。
      执行 AI 漏写 S10 或把注释改回去，`-DocCite` 仍然 exit=0。**写了不跑。**
    - 缺口 2：`batch2_preflight.py` 的 S9 仍用「Receive 之后第一处」旧规则，
      而 §19.3.3 订正 7 已改成双边界区间。**跑的是旧规则。**
    **判据：新增一个门禁脚本后，必须做三件事——
    (1) grep 确认它被 CI/verify 真正调用（不是只存在）；
    (2) 验证「该红时红、该绿时绿」两条路径；
    (3) 若同一规则在多处出现（文档 + 脚本），改一处必须同步另一处。**
    更细一层：**一次性门禁要加开关**（`-PreBatch1` / `-PostBatch2`），
    否则修复前必然红、修复后必然绿，无条件接入会让门禁永久失效。

## 设计原则（E6-E10 沉淀）
- 协议解析一律使用显式偏移 + 边界检查的 Reader，禁止 memcpy 结构体直接映射（对齐/端序风险）。
- 解码函数返回三态：Ok / NeedMoreData / Invalid*，便于流式解析与断链判定。
- 长度字段与实际数据必须一致性校验（TPKT 规范明确要求）。
- 不使用第三方依赖起步（避免 vcpkg/网络依赖），加密层自带实现（已落地）。

## 崩溃取证（2026-10-22 沉淀，用户明确要求）
- **根因**：Windows 未处理异常默认交给 WER，弹出模态对话框 → 进程挂住 → 自动化流水线
  看到的是"超时"而不是"失败"，等于把崩溃信息全部丢掉。只装
  `SetUnhandledExceptionFilter` + `CaptureStackBackTrace` 而没有关 WER、没有 minidump，
  仍然会阻塞。
- **正确做法**（`src/util/crash_guard.cpp`，`rtsc::util::InstallCrashGuard`）：
  1. `SetErrorMode(SEM_FAILCRITICALERRORS|SEM_NOGPFAULTERRORBOX|SEM_NOOPENFILEERRORBOX)`
     —— 关掉 GPF 弹窗，这是"不阻塞"的关键。
  2. `_set_error_mode(_OUT_TO_STDERR)` + `_set_abort_behavior(0, _WRITE_ABORT_MSG|_CALL_REPORTFAULT)`
     —— CRT abort 不再进 WER。
  3. `_CrtSetReportMode/_CrtSetReportFile(_CRT_ASSERT|_CRT_ERROR → STDERR)`
     —— assert 对话框改到 stderr。
  4. `SetUnhandledExceptionFilter` + `MiniDumpWriteDump`（ThreadInfo|UnloadedModules|
     ProcessThreadData）+ 文本报告（异常码/地址/模块+偏移/参数/符号化栈）。
  5. `set_terminate` / `_set_purecall_handler` / `_set_invalid_parameter_handler` /
     `signal(SIGABRT)` 全部接管。
  6. 收尾 `TerminateProcess(..., 3)` —— 用非零退出码，让 ctest 立刻判失败。
- **回溯必须最先抓**：`CaptureStackBackTrace` 要在 `CaptureAndDie` 入口调用（`skip+1`），
  否则栈顶全是 crash-guard 自己的帧。
- 输出目录：`RTSC_CRASH_DIR` 环境变量优先，否则 `<exe目录>\crashes`。
- 验证入口：`verify.ps1 -CrashCheck`（三种模式 null/abort/terminate，每个独立目录，
  60s 未退出即判 FAIL，并断言 reason 行与模式匹配）。
- 测试统一入口 `tests/test_main.h` 的 `rtsc::test::run_all(app)`：装 guard + 跑用例 +
  失败时打印 dump 目录，避免每个测试文件重复 main。

## MCS 层事实（2026-10-22 规范核实，推翻早期假设）
- **1002 是 Server Channel（固定 `0x03EA`），不是 I/O 通道、也不是用户通道**。
  客户端**不 join** 1002；它只作为 server→client Send Data Indication 的 `initiator`。
- 客户端 join 顺序（[MS-RDPBCGR] 3.2.5.3.8）：User Channel（Attach User Confirm 分配）→
  I/O Channel（SC_NET 的 `MCSChannelId`）→ Message Channel（仅当非 0）→ Static VC
  （SC_NET 的 `channelIdArray`，顺序与 CS_NET 请求一致）。
- 除 1002 外**所有 channel id 都由服务器指定**，不是规范固定值。
- UserId 编码 = `(id - 1001)` 的 u16 大端；ChannelId 编码 = 原值 u16 大端。
- `DynamicChannelId ::= ChannelId (1001..65535)`；[MS-RDPBCGR] 3.3.1.2 写的
  "1001 to 65536" 与 T.125 冲突，取 T.125。
- Send Data 的 `dataPriority|segmentation|padding` 字节恒为 `0x70`。
  choice 25=`0x64`（请求）、26=`0x68`（指示）。
- Send Data 的 `userData` 上限 **16383**（[MS-RDPBCGR] 2.2 禁止 PER 分片形式）。
- DPU：`21 80` 共 2 字节；[MS-RDPBCGR] 2.2.2.3 写 "mcsDPum (8 bytes)" 是笔误。
- `Result` 枚举 16 值、`Reason` 枚举 5 值；RDP 侧 Result 只用 0 与 14，
  Reason 只用 1（provider-initiated）与 3（user-requested）。
- Fast-Path **不经** TPKT/X.224/MCS，连接建立全程走慢路径。
- GCC 内层长度是 **PER 14-bit determinant**（非 BER），正确上限 `0x3FFF`。
- `h221NonStandard` 是 4 字节 ASCII（"Duca" 客户端 / "McDn" 服务器），前置 1 字节
  PER 长度决定因子（len−4=0）。

## 密码学与许可层事实（2026-10-22 落地）
- 自带实现（`src/crypto/hash.cpp`）：MD4 / MD5 / SHA-1 / HMAC-MD5 / RC4。
  MD4 只为 NTLM 的 NT hash 保留——换成 SHA-* 会直接导致认证失败。
- RC4 是**有状态**流密码：许可的 MAC/加密对、NTLM 的 SEAL 都要求同一实例连续推进。
  用独立实例算 checksum 会得到错误值（已被 [MS-NLMP] 4.2.4.4 向量的红证确认）。
- 许可 L3 密钥派生（[MS-RDPELE] 5.1.2）：
  `SaltedHash(S,I) = MD5(S || SHA1(I || S || ClientRandom || ServerRandom))`，
  `SaltedHash2` 的随机数顺序**相反**（ServerRandom 在前）。这是最易写错的地方。
  `'A'/'BB'/'CCC'` 是字面字符串，不是重复字符。
  `MAC-salt-key` = SessionKeyBlob 前 16 字节；
  `LicensingEncryptionKey` = MD5(后 16 字节 + ClientRandom + ServerRandom)。
- 许可 MAC（5.1.5）= `MD5(mac_salt_key || pad2 || SHA1(mac_salt_key || pad1 ||
  LE32(len) || data))`，pad1 = 40×0x36，pad2 = 48×0x5C，输出**完整 16 字节**
  （不是 Standard RDP Security 的 8 字节截断）。
- `ERROR_ALERT(0x07, 0x02)` = `STATUS_VALID_CLIENT` + `ST_NO_TRANSITION` 是**成功**信号，
  不是失败。当成失败会自己掐断连接。
- `wBlobLen == 0` 时 `blobData` **不出现在线上**（不是"存在但为空"）。
- `EncryptedPlatformChallenge.wBlobType` / `EncryptedHWID.wBlobType` 服务器发垃圾值或
  `0x0001`（官方 dump 即如此），**禁止校验**。
- `NEW_LICENSE_INFO.pbScope` 是 **ANSI**，同结构内 `pbCompanyName`/`pbProductId` 是
  **UTF-16LE**（官方 dump 并存，硬证据）。
- HYBRID_EX 下 L3（许可内部 RC4）**仍然加密**；TLS 只替代 L2（Standard RDP Security），
  只免除 `SEC_LICENSE_ENCRYPT_CS/SC` 标志。
- RSA 是 **raw**（`c = r^e mod n`，无 PKCS#1/OAEP），线上格式 6 字段
  `magic/keylen/bitlen/datalen/pubExp/modulus`，modulus 尾部有 **8 字节零填充**并计入 keylen。
  Windows 实际用 2048-bit（`keylen=264`），规范正文写 512-bit 是过时描述。
- 许可阶段有两条路径：personal terminal server 走**零许可消息**（只解析 16 字节
  ERROR_ALERT）；application server mode 必须走完整 13 步。运行时按 bMsgType 分支，
  禁止编译期写死。

## 安全层事实（2026-10-22 规范核实 + 实机红证）
- **CredSSP 在 TLS 之上**：X.224 CCF（明文）→ TLS 握手 → TSRequest×5（全在 TLS 内）→
  EUAR 4 字节裸 PDU（仅 HYBRID_EX）→ MCS Connect Initial（在 TLS 内）。
- 目标 192.168.1.7:3389 强制 `PROTOCOL_HYBRID_EX`（0x08）：
  `RDP_NEG_RSP flags=0x0F selectedProtocol=0x08`。
- pubKeyAuth v5/6：`SHA256("CredSSP Client-To-Server Binding Hash\0" || nonce ||
  SubjectPublicKey)` 再经 NTLM SEAL 封装成 `LE32(1)||checksum||LE32(0)||ciphertext`，48 字节。
  `SubjectPublicKey` 是证书 SPKI 里的 BIT STRING 去掉 unused-bits 字节，
  **不是**整证书、**不是**整 SPKI、**不是**指纹。
- 本服务器要**裸 NTLM blob**；用 SPNEGO negTokenResp 包会返回 `SEC_E_INVALID_TOKEN`。
- 客户端发 version 1..8，服务器恒回 6。

## TLS 后端事实（2026-10-22 实机实测，推翻 security-layer.md §8 结论）
- **Windows 侧零依赖可行**：SChannel 对真实 RDP 服务器完成 TLS 1.2 握手，
  `protocol=0x0800`、`cipher=0x6610`（TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384）、
  `stream sizes: header=13 trailer=16 maxmsg=16384 block=16`，**2 轮往返**完成。
- **SPKI 导出**：`CryptEncodeObjectEx(X509_PUBLIC_KEY_INFO)` 作用于
  `cert->pCertInfo->SubjectPublicKeyInfo` → **294 字节** DER，与证书 DER 偏移 134 处逐字节相同。
  CredSSP pubKeyAuth 用的是其中 **270 字节**（去掉 24 字节 SPKI 头）。
  把整张证书传给 `CryptDecodeObjectEx(X509_PUBLIC_KEY_INFO)` 会 **0xC0000005 访问违例**。
- **进程内回环可行**（`evidence\tls\loopback_schannel.cpp`，`RESULT=PASS`）：
  同进程 INBOUND + OUTBOUND 双上下文，2 轮握手，双向应用数据、双记录 `SECBUFFER_EXTRA`、
  截断记录 `0x80090318` 全部符合预期。这是 TLS 层红证的主路径。
- **SChannel 流上下文三个必踩的坑**：
  ① `DecryptMessage` 的 `sb[0]` 必须是 `SECBUFFER_DATA` + **完整记录**（含 5 字节头）；
     `SECBUFFER_STREAM` 是 datagram 上下文用法，用了会 `0x80090308 SEC_E_INVALID_TOKEN`。
  ② `ISC_REQ_ALLOCATE_MEMORY` 与预分配 `SecBuffer` **不能同时用** —— SChannel 会替换
     `pvBuffer`，导致发出垃圾字节 → 对端 `0x80090331 SEC_E_ALGORITHM_MISMATCH`。
  ③ 每轮复用同一个输出 vector 必须 `clear()`，否则 token 被回喂给自己。
- `SP_PROT_TLS1_2_CLIENT`(0x800) / `SP_PROT_TLS1_2_SERVER`(0x400) 是**方向标志**不是版本号；
  判版本要看 `SECPKG_ATTR_CONNECTION_INFO.dwProtocol` 的完整掩码。
- **选型结论**：双后端 + 后端无关接口。Windows=SChannel（零依赖，已验证），
  Linux=OpenSSL（后续）。**禁止**用系统 `CredSSP` SSP —— 会把 pubKeyAuth/NTLM 整个黑盒化，
  与"逆向重写协议栈"的项目目标冲突。NTLM/CredSSP 一律自研。
- 环境无 vcpkg / perl / nasm / OpenSSL，`security-layer.md` §8.2 的三条 Windows 集成路径
  在当前环境**全部不可用**；且 §8 建议的 `find_package(OpenSSL REQUIRED)` 会让整个工程
  configure 失败、所有测试套件全灭，直接违反零依赖硬约束。
- 红证 harness 保真度 5 条（由双向批评沉淀）：①不得添加被建模代码没有的检查；
  ②不得遗漏被建模代码已有的检查；③建模判定必须在报告中显式声明"这是建模结论"；
  ④必须另附逐字实现交叉验证；⑤下溢/回绕按真实语义建模并注明。

147. **安全层接入的核心约束：阶段与缓冲区必须同属一个所有者**（2026-10-24 第27轮）。
    同一条 TCP 字节流在连接建立期要依次被切成四种单位：TLS record / CredSSP DER 自定界 /
    EUAR 固定 4 字节 / MCS TPKT。谁决定"从缓冲区头部消费几个字节"，谁就必须同时知道"现在是什么阶段"。
    拆到两个对象必然产生 split-brain。实现：SecurityLayer 持有单一 pending_cipher_，
    Step() 追加后跨阶段循环推进。
148. **EUAR 不会被误当 MCS，但会被"静默吞掉"**（2026-10-24）。
    TpktStream 在头部不是 03 00 时逐字节前扫并丢弃；AUTHZ_SUCCESS 与 AUTHZ_ACCESS_DENIED
    都会被当垃圾丢掉。结果：授权被拒也"看起来连上了"。必须有一个显式的"恰读 4 字节"阶段。
149. **驱动器不能在 kWrite 后重复 pump**（2026-10-24 第27轮，实测缺陷）。
    ConnectionDriver::DriveSecurity 初版在 want==kWrite 后 continue 再调 Step(nullptr,0)，
    而脚本化 TLS 每次调用都推进一轮，导致 TLS 握手被无输入推到第 2 轮完成。
    正确语义：kWrite 即返回（调用方写完再读再调 OnData）。
    "循环直到需要输入"不等于"循环直到无输出"。

150. **HYBRID_EX 下除 Client Info/licensing 外无 RDP security header**（2026-10-24 第29轮）。
    docs/spec/security-layer.md §1.3：[MS-RDPBCGR] 5.4.4 原文
    "Because RDP encryption is not used in the presence of an External Security Protocol layer,
    the security header data is not present in any RDP traffic (except for the Client Info and
    licensing PDUs)"。
    所以 Demand Active / Synchronize / Control / FontMap 等慢路径 PDU 的 share control header
    直接跟在 MCS payload 之后。licensing PDU 用 4 字节 Basic 头（flags = SEC_LICENSE_PKT 0x0080）
    区分。把 security header 当成"总是存在"会让整个数据面偏移 4 字节且无错误码。
151. **会话建立状态机（S0-S6）的分支完备要点**（2026-10-24 第29轮，capabilities.md §12）。
    - S1 收 pduType 不符 -> **忽略**；长度不符 -> **断链**（两者处置相反，不能合并）
    - Confirm Active 发出后**立即**获得 input 发送许可（不等 Server Synchronize）；
      但服务端在收到 Font List 之后才发图形（两者不对称）
    - S5（Deactivate All）**不重跑** MCS/安全层/licensing，只重跑能力交换与最终化
    - 未列出的 (state, event) 一律忽略并告警，不改状态、不断链
    - Font Map 是连接序列最后一个 PDU，收到它才是 S4

152. **RDP 的 RSA 不是 PKCS#1，是原始 RSA**（2026-10-24 第30轮，已联网核实）。
    [MS-RDPBCGR] 5.3.4.1 原文：`c = r^e mod n`，且 "The client random value is interpreted
    as an unsigned **little-endian** integer value"，结果拷进 `(bitlen/8)+8` 字节的零缓冲。
    三个易错点：①无填充（不是 PKCS#1 v1.5）②输入小端 ③输出多 8 字节零尾。
    任一处错，服务器解不出 premaster，症状只是"连接被断"，无错误码。
    实现：Windows BCrypt（`BCRYPT_PAD_NONE`），输入反序并左填充到模长。
    与 TLS 的 RSA（PKCS#1 v1.5）**完全不同**，禁止复用同一段代码。

153. **许可 L3 加密与 TLS 无关，永远存在**（2026-10-24 第31轮，licensing.md §6.1）。
    只要走 NEW_LICENSE_REQUEST 路径，就必须实现许可自身的 RC4 + MD5 MAC 层：
    48 字节 premaster + 32 字节 client random 用服务器 RSA 公钥加密，
    Encrypted* 字段用许可加密密钥 RC4 加密。HYBRID_EX 下 TLS 只保护外层，
    L3 是内层独立保护——**不能因为"有 TLS 了"就跳过 L3**。
    L3 密钥派生两轮的 random 顺序相反（SaltedHash 是 CR||SR，SaltedHash2 是 SR||CR），
    这是最常写错处；MasterSecret 是 48 字节（3×16），不是 32。
154. **许可 PDU 是 HYBRID_EX 下仅有的两种带 security header 的 PDU 之一**
    （2026-10-24，security-layer.md §1.3）。许可 PDU 带 4 字节 Basic 头（flags = SEC_LICENSE_PKT 0x0080）；
    其余慢路径 PDU 无头。所以"收到第一个 PDU 先看前 2 字节是否是 0x0080"是区分许可与能力交换的判据。

155. **Standard RDP Security 与许可 L3 的密钥派生相似但不同**（2026-10-24 第33轮，已用 FreeRDP 交叉核对）。
    两者都是 `SaltedHash(S,I)=MD5(S+SHA1(I+S+CR+SR))` 的链，但：
    | | PreMasterSecret | SessionKeyBlob 标识符 | SessionKeyBlob 的 random 顺序 |
    |---|---|---|---|
    | Standard RDP Security | First192Bits(CR)+First192Bits(SR) | X / YY / ZZZ | CR \|\| SR（同 SaltedHash） |
    | 许可 L3 | RSA 解密的 48 字节 | A / BB / CCC | SR \|\| CR（SaltedHash2） |
    **禁止把两者合并成一个函数**。标识符长度也不同（'X'=1, 'YY'=2, 'ZZZ'=3）。
    算法已用 FreeRDP `libfreerdp/core/security.c`（security_establish_keys/security_A/security_X）逐行核对。
156. **差分测试的「独立实现」也可能自己错**（2026-10-24 第33轮）。
    我写的 Python hashlib 参考实现把 `b'ZZ'` 写成了 `b'ZZZ'`（少一个 Z），
    结果 EncryptKey 期望值错，被 C++ 实测抓出（Python 错，C++ 对）。
    **教训：差分测试发现不一致时，先假设「任一方都可能错」，用第三信息源（规范原文/FreeRDP）裁决，
    不能默认「被测代码错」。** 这与 memory 规则 26（驳回前先验证前提）同族。

157. **RDP 加密顺序：MAC 先于 RC4，且 MAC 覆盖明文**（2026-10-24 第34轮，已核实官方原文）。
    [MS-RDPBCGR] 5.3.6 逐字："First, a MAC value is generated over the unencrypted data.
    Next, the data block is encrypted with RC4 using the current client or server encryption
    substitution table." 解密是反序：先 RC4 解密，再对明文算 MAC 比对。
    **易错点**：若先加密再对密文算 MAC，或解密后对密文算 MAC，两边都自洽但都与服务器不兼容。
158. **Standard RDP Security 每 4096 包必须更新密钥**（2026-10-24，[MS-RDPBCGR] 5.3.6.1）。
    key = RC4(key, MD5(update_key + pad2 + SHA1(update_key + pad1 + key)))，
    update_key 是**初始**密钥（不随更新变），40/56-bit 更新后再套盐。
    RC4 是流密码，不更新会让密钥流超过安全长度。收发两个方向**各自**独立计数与更新。
    测试方法：跑 >4096 包并跨边界，两端必须仍能互解（否则说明只更新了一端或计数不同步）。

159. **Fast-Path 的两个头位序必须分开记**（2026-10-24 第35轮，已核实官方原文 + 4.7 dump）。
    - **事件头**（TS_FP_INPUT_EVENT::eventHeader，1 字节）= `eventFlags`(低 5 位) | `eventCode`(高 3 位)。
      证据：官方 4.7 dump `0x20` → eventCode=1(MOUSE)、eventFlags=0。
    - **PDU 头**（TS_FP_INPUT_PDU::fpInputHeader，1 字节）= `action`(低 2 位) | `numEvents`(4 位) | `flags`(高 2 位)。
      证据：官方 4.7 dump `0xc4` → action=0、numEvents=1、flags=0x3(ENCRYPTED|SECURE_CHECKSUM)。
      **numEvents 是 4 位（不是 5 位）**；>15 事件时该 4 位写 0，并在 dataSignature 之后插 1 字节扩展计数。
    两个头都容易把「低 5 位 vs 高 3 位」记反，一旦记反所有事件类型都会错位。

160. **Fast-Path 更新头与「字段存在」vs「数据压缩」是两回事**（2026-10-24 第36轮）。
    - `TS_FP_UPDATE::updateHeader` = `updateCode`(低 4 位) | `fragmentation`(2 位) | `compression`(2 位)。
      `compression == 0x2` 只表示**后面有一个 compressionFlags 字节**（字段存在），
      **不表示数据已压缩**；数据是否真压缩看 `compressionFlags & PACKET_COMPRESSED (0x20)`。
      两者混为一谈会导致：把未压缩数据当压缩去解，或漏读/多读 1 字节导致后续全部错位。
    - 更新数据长度 `size` 是 u16 LE，位于 updateHeader [+compressionFlags] 之后。
      解析必须按 `size` 前进而不是按「结构预期长度」，否则遇可变长 payload（位图/指针）必错。

161. **RDP 未压缩位图：自底向上 + 每行补齐到 4 字节**（2026-10-24 第37轮，已核实官方原文）。
    [MS-RDPBCGR] 2.2.9.1.1.3.1.2.3 逐字："Uncompressed bitmap data is formatted as a
    bottom-up, left-to-right series of pixels. Each pixel is a whole number of bytes.
    Each row contains a multiple of four bytes (including up to three bytes of padding,
    as necessary)."
    - **自底向上**：wire 第 0 行是图像最后一行；转成顶向下要整行倒序。
    - **4 字节行补齐**：1x1 的 16bpp 也要 4 字节；按 `width*bpp/8` 算长度会短读。
    注意与 RLE 的 `scanWidth`（2 字节对齐）区分——两者对齐单位不同。
162. **像素字节序**：24bpp 是 BGR、32bpp 是 BGRA（不是 RGB/RGBA）。
    16bpp 是 RGB565（R 5 位在最高、G 6 位居中、B 5 位最低），15bpp 是 RGB555。
    位扩展用 `(v << n) | (v >> (width - n))`（如 5 位 -> `(v<<3)|(v>>2)`）以保证 0/满量程映射正确。

163. **RLE 位图压缩序的分派规则**（2026-10-24 第38轮，[MS-RDPBCGR] 2.2.9.1.1.3.1.2.4）。
    三种形式共存于一个字节流，分派顺序必须是：
    1. `h >= 0xF0`：扩展序（0xF0-0xF8 MEGA_MEGA_*，0xF9/0xFA SPECIAL_FGBG，0xFD/0xFE WHITE/BLACK）
    2. `(h & 0xF0) == 0xC0/0xD0/0xE0`：LITE 形式（4 位 code = h>>4，4 位 run = h&0x0F）
    3. 否则：REGULAR 形式（3 位 code = h>>5，5 位 run = h&0x1F）
    run 为 0 表示 MEGA：跟一个字节，REGULAR 加 32 / LITE 加 16；FGBG_IMAGE 例外（加 1，
    且非 MEGA 时 run = (h&0x1F)*8）。
    **不能只按 `h>>5` 分派**：LITE 的 0xC/0xD/0xE 会被误判成 REGULAR 的 6/6/7。
164. **RLE 的三个语义细节**（2026-10-24 第38轮）：
    - FG 色初值 = 白；FGBG 的 1 位 = `上一行像素 XOR 当前 FG`（首行则是 FG 本身），
      0 位 = 上一行像素（首行则是黑）。
    - 连续两个 BG 序之间必须补 1 个 FG 像素（且计入长度）；**唯一例外**是
      第一个 BG 在首行、第二个在次行——此时不补。
    - 抖动序（DITHERED_RUN）的 run 是**像素对数**，不是像素数。

165. **虚拟通道分块的三个不变量**（2026-10-24 第39轮，[MS-RDPBCGR] 2.2.6.1.1 / 2.2.6.1）。
    - `CHANNEL_PDU_HEADER.length` 是**整条消息**的未压缩总长，**每个分块都写同一个值**，
      不是本块长度。按「本块长度」理解会让重组永远对不上。
    - 单块消息必须**同时**置 `FIRST|LAST`；中间块**都不置**；顺序不可乱（无位置字段）。
    - 所有分块消息必须置 `CHANNEL_FLAG_SHOW_PROTOCOL (0x10)`，否则接收方无法重组。
    - 未协商 VCChunkSize 时，线上每块 <= 1600 字节。

166. **Surface Commands 的 cmdLength 是自包含的**（2026-10-24 第41轮，[MS-RDPBCGR] 2.2.9.2）。
    TS_SURFCMD = `cmdType(2) + cmdLength(2) + cmdData`，其中 **cmdLength 含 4 字节头**。
    遍历必须按 cmdLength 前进；`cmdLength < 4` 必须判畸形（否则原地死循环）。
    一个 FastPath SURFCMDS 更新（code 4）可携带多个 TS_SURFCMD，按序处理。
    Set Surface Bits 的 cmdData 内含一个 Extended Bitmap Data（含实际 width/height/bpp/编码数据），
    destRight/destBottom 是 exclusive 且规范说 SHOULD 被忽略——尺寸以 Extended Bitmap Data 为准。

167. **虚拟通道协议层是「通道数据」而非「整帧」**（2026-10-24 第42轮，cliprdr）。
    cliprdr 的 CLIPRDR_HEADER（msgType u16 + msgFlags u16 + dataLen u32）是**通道数据**的头部，
    外面还要套 `CHANNEL_PDU_HEADER`（8 字节，见规则 165）。两层头各有各的 length：
    - CHANNEL_PDU_HEADER.length = 整条通道消息的未压缩总长（分块重组用）
    - CLIPRDR_HEADER.dataLen = 本 PDU 的 payload 长度（单条消息内）
    混淆两者会把通道重组和协议解析搅在一起。所有虚拟通道协议（cliprdr/rdpdr/rdpsnd/drdynvc）
    都遵循这个「两层头」结构。
168. **cliprdr Format List 是 u32 数组，长度必须是 4 的倍数**（2026-10-24，[MS-RDPECLIP] 2.2.3）。
    非 4 倍数说明解析错位（或用了 Short Format Name 变体 + CB_ASCII_NAMES），必须判畸形而非静默截断。

169. **drdynvc 头的位序与变长 ChannelId**（2026-10-24 第43轮，[MS-RDPEDYC] 2.2）。
    DYNVC_HEADER 1 字节 = `cbId(2, 低) | Sp(2) | Cmd(4, 高)`：
    `cbId = h & 0x03`、`Sp = (h >> 2) & 0x03`、`Cmd = h >> 4`。
    **cbId 在低位（不是高位）**，写反会让所有命令类型错位。
    ChannelId 宽度由 cbId 决定：0->1 字节、1->2 字节、2->4 字节、**3 非法必须拒绝**。
    这是 RDP 里少见的「头部自带字段宽度」设计，解析前必须先读 cbId 才能知道读几个字节。

170. **RDPDR_HEADER 是 4 字节，没有 PacketLength**（2026-10-24 第44轮，官方 dump 佐证）。
    [MS-RDPEFS] 2.2.1.1 的 RDPDR_HEADER = `Component(2) + PacketId(2)`，共 4 字节。
    官方 2.2.2.2 的 Server Announce dump 是 12 字节：
    `72 44 6e 49 | 01 00 | 0c 00 | 01 00 00 00`（Component | PacketId | VersionMajor | VersionMinor | ClientId），
    **紧跟 header 的是 VersionMajor 而不是长度**。长度由外层虚拟通道 PDU 隐式给出。
    （FreeRDP 的 RDPDR_HEADER 结构体里带 PacketLength，与规范不符——**以规范和官方 dump 为准**。）

171. **rdpsnd 的 SNDPROLOG.BodySize 在 SNDC_WAVE 下语义不同**（2026-10-24 第45轮，[MS-RDPEA] 2.2.1）。
    SNDPROLOG = `msgType(1) + bPad(1) + BodySize(2)`，共 4 字节。
    对**除 SNDC_WAVE(0x02) 之外**的所有类型，BodySize = 其后数据的字节数；
    但 SNDC_WAVE 时 BodySize 的含义由 2.2.3.3 的 Header 字段另行定义（不是简单长度）。
    解析器必须按 msgType 分支，不能对 SNDC_WAVE 直接用 BodySize 当长度。

172. **RDP 6.0 位图（RDP6_BITMAP_STREAM）与 NSCodec 是两个不同编解码器**（2026-10-24 第46轮）。
    - `RDP6_BITMAP_STREAM`（[MS-RDPEGDI] 2.2.2.5）是**整幅位图**的 AYCoCg/ARGB 平面编码，
      用于 Bitmap Update / Fast-Path Bitmap Update / Cache Bitmap Rev1/Rev2 的 bitmapData。
    - `NSCodec`（[MS-RDPNSC]）是**分块（tile）**编解码器，用于 Set Surface Bits / Cache Bitmap Rev3。
    两者外观相似（都叫「RDP 6.0 压缩」）但结构完全不同，禁止混用。
173. **RDP6 FormatHeader 的 CS 位与 CLL 有依赖**（2026-10-24，[MS-RDPEGDI] 2.2.2.5.1）。
    FormatHeader = `CLL(3, 低) | CS(1) | RLE(1) | NA(1) | Reserved(2, 高)`。
    CLL=0 表示 ARGB 色彩空间；CS（chroma subsampling）**只对 AYCoCg 适用**，
    故 CS=1 且 CLL=0 是非法组合，必须拒绝。
    RDP6 RLE 的 controlByte = `nRunLength(4, 高) | cRawBytes(4, 低)`，**不得为 0**；
    nRunLength=1/2 是扩展长 run 编码（run=16+cRaw / 32+cRaw），此时无 RAW 字节。

174. **RDP 6.0 RLE 平面的行差分是「累加」而非「绝对」**（2026-10-24 第47轮，[MS-RDPEGDI] 3.1.9.2）。
    RLE 解码出的平面字节不是最终值：**第 0 行是绝对值，第 y 行（y>=1）的每个字节是「delta」**，
    还原时 `plane[y][x] = plane[y][x] + plane[y-1][x]`（8-bit mod 256）。
    这是**空间差分**（与上一行比较），不是时间差分。忘记这步会得到「整体对但逐行偏移」的图，
    看起来像「颜色渐变」而不像错误。
    raw 平面（RLE=0）不做差分；此时平面后还有 1 字节 Pad（可忽略）。

175. **无官方向量的编解码器必须找第三方权威实现交叉核对**（2026-10-24 第48轮，RDP6）。
    RDP6 RLE 我按规范文字实现了两处，都错：
    - controlByte 半字节顺序（规范位图「低位在左」→ nRunLength 在低 4 位）
    - 行差分是「符号-幅值」编码（bit0=符号，`d>>1` 是幅值），不是无符号累加
    **两处都自洽通过了我自造的测试**——因为测试数据是按同样的错误假设构造的。
    只有对照 FreeRDP `planar.c` 才暴露。
    **判据：自造测试只能验证「实现与我的理解一致」，不能验证「理解正确」。
    没有官方向量时，必须找第三方权威实现（FreeRDP/微软测试套件）逐位域核对。**
    与规则 38（自指测试无检出能力）、规则 23（差分测试需信息源不同）同族。
176. **规范位图的方向：字段顺序 = 位序从低到高**（本项目已多次踩）。
    RDP 规范里的 bitmask 图（如 FastPath `action | numEvents | flags`、
    RDP6 `nRunLength | cRawBytes`）**最左字段是最低位**。
    实例：`action = h & 0x03`（低 2 位）、`nRunLength = cb & 0x0F`（低 4 位）。
    按「最左=最高位」理解会全部写反，且错误在自洽测试下不可见。

177. **RDP YCoCg 逆变换的具体形式**（2026-10-24 第49轮，FreeRDP prim_YCoCg.c 交叉核对）。
    ```
    T = Y - Cg;  R = T - Co;  G = Y + Cg;  B = T + Co;   // 各分量 clamp 0..255
    ```
    **注意 R 用减 Co、B 用加 Co**（与直觉相反；规范矩阵写 1/2 系数，FreeRDP 把 /2 折进色度移位）。
    色度字节转有符号：`(int8_t)(raw << (CLL - 1))`。
    我初版把 R/B 写反（R=T+Co），被测试抓出 R/B 值互换。
    平面顺序：Alpha(可选) / Y / Co / Cg；CS 时 Co/Cg 为 (w+1)/2 × (h+1)/2 并上采样 2x2。

178. **NSCodec 的结构要点**（2026-10-24 第50轮，FreeRDP nsc.c 交叉核对）。
    - 头 20 字节：`PlaneByteCount[4]`（各 u32 LE）+ `ColorLossLevel`(1..7) + `ChromaSubsamplingLevel` + 2 保留。
    - **平面顺序 = Y, Co, Cg, A**（不是直觉的 A 在前）。
    - 平面按 PlaneByteCount 判定：`==0` → 填 0xFF（全不透明）；`< originalSize` → RLE；`== originalSize` → 原样。
    - NSCodec RLE 与 RDP6 RLE **完全不同**：
      `value value <len>` 表示 run，len<0xFF 时实际长度 = len+2，len==0xFF 时后跟 u32 LE；
      **最后 4 字节永远是原样拷贝**（不参与 RLE）；`left==5` 时单字节特殊处理。

179. **NSCodec 与 RDP6 的 Co 符号约定不同**（2026-10-24 第51轮，各自 FreeRDP 文件交叉核对）。
    - RDP6（planar.c/prim_YCoCg.c）：`T=Y-Cg; R=T-Co; G=Y+Cg; B=T+Co`
      → 展开：R = Y - Co - Cg，B = Y + Co - Cg
    - NSCodec（nsc.c）：`R=Y+Co-Cg; G=Y+Cg; B=Y-Co-Cg`
    **两者 R/B 的 Co 符号相反**。禁止复用同一个 AYCoCg 逆变换函数。
    另：NSCodec 的 Y 平面行 stride 补齐到 8（`ROUND_UP(width,8)`），不是 width。
    色度字节始终是**有符号**：`(int8_t)(raw << (CLL-1))`（0x80 = -128，不是 128）。

180. **RDP 绘制序的两种变长整数编码**（2026-10-24 第52轮，[MS-RDPEGDI] 2.2.2.2.1.2.1）。
    - 两字节编码：首字节**最高位为 0** → 值 = 该字节（1 字节）；为 1 → 值 = `((b0 & 0x7F) << 8) | b1`（2 字节）。
    - 四字节编码：首字节最高位为 0 → 值 = 该字节（1 字节）；为 1 → 值 = `((b0 & 0x3F) << 24) | (b1<<16) | (b2<<8) | b3`（4 字节）。
    注意四字节编码的**首字节只贡献低 6 位**（0x3F），不是 7 位（两字节编码才是 7 位）。
    解析必须返回消耗字节数（1 或 2/4），不能假设固定宽度。
181. **CACHE_BITMAP_REV2_ORDER 的 extraFlags 位域**（2026-10-24，[MS-RDPEGDI] 2.2.2.2.1.2.3）。
    `extraFlags`(u16) = `cacheId`(3, 低) | `bitsPerPixelId`(4) | `flags`(9, 高)。
    flags：`HEIGHT_SAME_AS_WIDTH`(0x01，置位则**高度字段省略**，高度=宽度) /
    `PERSISTENT_KEY_PRESENT`(0x02，置位则 key1+key2 存在) /
    `NO_BITMAP_COMPRESSION_HDR`(0x08) / `DO_NOT_CACHE`(0x10，cacheIndex 必须=32767)。
    bitsPerPixelId：0x3=8 / 0x4=16 / 0x5=24 / 0x6=32 bpp。

182. **新增 target 时必须把 `/W4 /WX` 放进 `if(MSVC)`**（2026-10-24 第53轮，真实阻断）。

185. **OpenSSL 内存 BIO 模式实现 TlsTransport 的要点**（2026-10-24 第54轮）。
    - `SSL_set_bio(ssl, rbio, wbio)`（两个 `BIO_s_mem`）；喂密文用 `BIO_write(rbio,...)`，
      取密文用 `BIO_read(wbio,...)`。`SSL_do_handshake`/`SSL_read`/`SSL_write` 返回 <0 时用
      `SSL_get_error` 区分 `SSL_ERROR_WANT_READ`（需更多输入）与真错误。
    - `consumed = in_size - (pending_after - pending_before)`（rbio 未消费字节 = pending 增量）。
    - `PeerSubjectPublicKey`（CredSSP 要的 BIT STRING 内容）：OpenSSL 3.0 的 `EVP_PKEY_get0_RSA`/
      `i2d_RSAPublicKey` 已废弃（-Werror=deprecated-declarations），改为**手工解析 SPKI DER**
      取 BIT STRING 内容，避免依赖废弃 API。
    - const 成员函数（PeerXxx/negotiated）内要设置 last_error_ 时，last_error_/terminal_ 必须 `mutable`，
      且 MakeError/Fail 必须是 const。
    - CMake 用 `option(RTSC_TLS_OPENSSL OFF)` 默认关：`find_package(OpenSSL REQUIRED)` 会让
      无 OpenSSL 的主机 configure 直接失败（design-a D5）。

186. **窗口抽象必须「未知后端如实报错」而不是静默回退 headless**（2026-10-24 第55轮）。
    `CreateWindow(w,h,"x11",why)` 在 X11 后端未接入时必须返回 nullptr + why，
    **禁止**悄悄返回 headless —— 静默回退会让「本应显示却没显示」变成无错误的黑盒。
    这与 G9「缺失即 FAIL 不静默 skip」同族。
187. **Surface 的 Blit 语义**（2026-10-24）：源矩形与目标表面求交后**逐行 memcpy**；
    越界像素忽略（不环绕）。`Blit(nullptr,...)` 与完全越界都是 no-op，不得崩溃。
    负坐标（如 (-1,-1)）是合法裁剪输入，不是错误。

188. **Win32 窗口后端的三个要点**（2026-10-24 第56轮）。
    - WndProc 里取回 C++ 实例：`WM_NCCREATE` 时从 `CREATESTRUCTW::lpCreateParams` 拿 this 指针，
      `SetWindowLongPtrW(hwnd, GWLP_USERDATA, ...)`；其余消息用 `GetWindowLongPtrW` 取回。
    - DIB 必须 `biHeight` 为**负**才是 top-down（与 Surface 的 top-down 一致），否则图像上下颠倒。
    - Surface 是 RGBA，Win32 DIB 是 BGRA：Present 时必须逐像素交换 R/B。
    - `RegisterClassExW` 第二个窗口会返回 `ERROR_CLASS_ALREADY_EXISTS`，必须容忍。
189. **窗口工厂的「默认 vs 具名」语义**（2026-10-24）：`backend==""` = 平台默认
    （Windows=win32，其它=headless）；**具名但未接入**的后端必须返回 nullptr + why，
    禁止静默回退 headless（否则「本该开窗却没开」变成无错误黑盒）。

190. **位图更新的解码器选择由 flags + bpp 决定**（2026-10-24 第57轮，图形合成管线）。
    `TS_BITMAP_DATA`：
    - `flags & BITMAP_COMPRESSION == 0` -> 未压缩（`DecodeRawBitmap`，行补齐 4 字节）
    - 压缩且 `bpp != 32` -> Interleaved RLE（`DecodeRleBitmap`）
    - 压缩且 `bpp == 32` -> RDP 6.0（`DecodeRdp6Bitmap`）
    - 若压缩且未置 `NO_BITMAP_COMPRESSION_HDR`，则 **bitmapDataStream 前有 8 字节 TS_CD_HEADER**，
      解码前必须跳过；漏跳会让所有压缩位图解错。
191. **FastPath 长度字段包含头与 length 自身**（2026-10-24 第57轮，测试两次踩）。
    `fpOutputHeader(1) + length(1或2) + Σupdate`；每个 update = `updateHeader(1) + size(2) + data`。
    长度字段=**整条 PDU 总字节数**。构造测试 PDU 时最容易漏 updateHeader 那 1 字节。
    且总长 > 127 时必须用 2 字节长度（`0x80|高7位`, 低 8 位），否则 length 被截断。

192. **X11 后端的三要点**（2026-10-24 第58轮）。
    - **命名冲突**：X11 的 `Window` 是 XID typedef，与本项目 `rtsc::ui::Window` 同名。
      在 `rtsc::ui` 命名空间内必须写 `::Window win_`，否则编译器把它解析成抽象基类。

    - `XCreateImage` 的 data 缓冲由 `XDestroyImage` 释放；若用自分配缓冲，只能随 image 一起销毁一次。

195. **Wayland 后端的三个要点**（2026-10-24 第59轮）。
    - wl_surface 的 shm 缓冲格式 `WL_SHM_FORMAT_XRGB8888` 在小端下字节序是 B,G,R,X；
      Surface 是 RGBA，Present 时必须交换 R/B。
    - listener 结构体随协议版本增加字段（xdg_toplevel 的 `wm_capabilities`、
      wl_pointer 的 `axis_value120`/`axis_relative_direction`）。用**指定初始化器**
      并抑制 `-Wmissing-field-initializers`，否则旧写法在新协议头下 `-Werror` 失败。
    - 输入：`wl_keyboard` 的 key 是 evdev scancode（减 8 得 set-1）；
      `wl_pointer` 的滚轮是 `axis` 事件（axis=vertical），不是按钮。

- [P7 集成] 端到端 `Client` = 连接驱动 + 图形管线 + 输入编码；`Connect` 用
  「先发 CRQ，再 读→OnData→写 循环」直到 `session_active()`；`Pump` 为单步循环。
  入站 PDU 分派：FastPath 判 `byte0 & 0x03 == 0`，慢速路径先 `McsSendData::parse`
  取 `user_data` 再 `SlowPathGraphicsUpdate::parse`。
- [接口约定] 会话激活后由 `ConnectionDriver::SetSessionPduHandler` 独占转交所有
  入站 PDU；驱动自身不再解释（路由函数开头 `session_->active()` 即 return），
  避免图形层与许可/会话机重复解析同一 PDU。
- [工具] 自动化验证脚本参数必须避免依赖「空字符串位置参数」——PowerShell 调原生
  程序会**吞掉空串实参**，导致 argc 错位（width/height/backend 全部左移）。
  需要可选空值时改用命名开关或占位符（如 `-`）。

196. **mstsc 的认证不在 mstscax.dll 里**（2026-10-25，REA 取证）：对 `C:\Windows\System32\mstscax.dll` 做 Ghidra 分析，

197. **NTLM CBT 的权威口径**（2026-10-25）：[MS-NLMP] 2.2.2.1 的 `MsvAvChannelBindings` = `MD5(gss_channel_bindings_struct)`；
    `application_data = "tls-server-end-point:" || SHA256(cert)`（**前缀必须有**，含冒号）。
    **权威依据 = Microsoft Open Specifications 官方博客《NTLM and Channel Binding Hash》的逐字节示例**（app_len=53/struct_len=73），
    与 **FreeRDP `libfreerdp/crypto/tls.c`**（`#define TLS_SERVER_END_POINT "tls-server-end-point:"` + `memcpy`）、**ldap3**/**ntlm-auth** 一致。
    **不要只凭 RFC 5929 §3 的 GSSAPI 段落推断**（那里 `tls-server-end-point` 是「channel binding unique prefix」，
    与 NTLM 的 `application_data` 构造口径不同）。
    结构布局：`initiator_addrtype(4)=0 + initiator_len(4)=0 + acceptor_addrtype(4)=0 + acceptor_len(4)=0 + app_len(4 LE) + app_data`。

198. **`MsvAvTargetName`(0x0009) = 目标服务器的 SPN**（2026-10-25，[MS-NLMP] 2.2.2.1 定义「The SPN of the target server」；
    3.1.1.2 `ClientSuppliedTargetName`）。RDP 场景即 `TERMSRV/<host>`（**不是** CHALLENGE 的 target_name）。
    规范 3.1.1.5 两分支：`not NULL → Value=SPN`；`NULL → Value=空串`（**都要发 AV_PAIR**，空串 Len=0，不得省略）。
    Unicode 且**不带结尾 NUL**。
