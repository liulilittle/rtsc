# 合并表算术核对（M01–M36）

主代理独立核对 `docs/spec/security-integration.audit-b.md` §9 的合并表。

## 1. 我最初的怀疑

看到统计行 `双方 12 / 仅甲 11 / 仅乙 12 / 撤销 1 = 36` 时，我先做了一次朴素验算：

```
甲 21 条 + 乙 23 条 − 重叠 12 = 32
+ S19/N6 (甲第二轮) + M36 (乙) + M31 (撤销) = 36      -> 与 36 一致
```

但接着按「归属」列验算时出现不一致：

```
双方 12 + 仅甲 11 = 23   （但甲只有 21 条）
双方 12 + 仅乙 12 = 24   （但乙只有 23 条）
```

两者各多 1。我一度判断这是**算术错误**。

## 2. 复核结论：不是错误，是 2 处一对多映射

逐行读表后确认，有两个原始缺陷各占两行合并记录：

| 原始编号 | 合并行 | 原因 |
|---|---|---|
| 甲 `S20` | **M25**（口令多份、无单一权威写者）+ **M27**（NLA 下 Client Info 仍回填明文口令） | 同一个缺陷的两个不同侧面：一个是「份数」，一个是「该不该发」 |
| 乙 `B17` | **M26**（`CS_SEC.encryptionMethods = 0x1B`）+ **M36**（`extEncryptionMethods` 也应置 0） | 同一结构体的两个字段 |

验算：

```
甲：21 条（S1..S21）+ N6 = 22 个原始项
    映射到 23 行（S20 占 2 行）-> 12 + 11 = 23   ✓
乙：23 条（B01..B23）
    映射到 24 行（B17 占 2 行）-> 12 + 12 = 24   ✓
合计行数：12 + 11 + 12 + 1(撤销) = 36            ✓
严重度：6 + 12 + 17 + 1 = 36                     ✓
```

## 3. 结论

**合并表算术正确**，36 行与两边原始条数完全自洽。多出的 1 行在两边各有一处，
且都已在表中用「（甲第二轮补）」「B17 补充」等标注可追溯。

## 4. 为什么记录这次核对

我最初的怀疑是**错的**。如果不追到底，会有两种坏结果：

1. 报告一个不存在的缺陷（制造噪音，且损害审计可信度）；
2. 反过来，如果真的是算术错误而我没查，合并表就成了定案基线，错误会传导到执行批次。

**判据**：当两个不同口径的验算给出不同结果时，先假设「两个口径对同一对象的计数规则不同」，
逐项找差异，再判断谁错。**不要直接宣布发现错误。**

## 5. 遗留

- 未逐行核对 M01–M36 的「症状」描述是否与甲/乙原文一致（只核了归属与条数）。
- 未核对「严重度」定级是否合理（例如 M12 从 P1 降为 P2 的依据）。
