=== S24-b RED BASELINE, recorded at batch-0 completion ===

PURPOSE
  Batch 0 (S21) changed the library structure: the public factory
  CreateTlsTransport moved into a new facade TU (src/net/tls_factory.cpp) and
  the SChannel backend was renamed to CreateSchannelTransport and split into its
  own static library. Because that restructure touched exactly the object that
  S24-b lives in, this file records the state of S24-b AT BATCH-0 COMPLETION,
  so batch 2 can prove "it was red before we fixed it" and not merely assert it.

  THIS IS NOT A BATCH-0 LEFTOVER.
  S24-b is a batch-2 (TLS backend) defect. Batch 0 neither fixes nor worsens it.
  Batch 0's job was only: build on Linux + keep Windows byte-identical.

--------------------------------------------------------------------------
DEFECT UNDER RECORD
--------------------------------------------------------------------------
  S24-b = src/net/tls_schannel.cpp:431

      if (st == SEC_E_OK || st == SEC_I_CONTINUE_NEEDED) {   // line 431
          closed_ = true;
          return MakeError(Status::kOk, st, "");             // line 433
      }

  During Shutdown, SEC_I_CONTINUE_NEEDED means "I started a renegotiation and
  you must keep going", which is the OPPOSITE of "gracefully closed". Mapping it
  to Status::kOk also sets closed_ = true, which short-circuits Receive and can
  strand buffered plaintext (S9 compounds this).

  The earlier audit claim was: "after fixing S24-a (the shutdown token) ISC
  returns SEC_E_OK, so the SEC_I_CONTINUE_NEEDED arm is unreachable, therefore no
  red test can be constructed, therefore S24-b is not separately catchable."
  That reasoning asked "can the product reach this arm via its happy path"
  instead of "is this mapping wrong". It is refuted below.

--------------------------------------------------------------------------
PART 1 — THE VIOLATION IS OBSERVABLE ON THE PRODUCT AS IT STANDS
--------------------------------------------------------------------------
  Probe: F:\rtsc\.tmp\probe_s24b\probe_s24b.cpp
  Build: F:\rtsc\.tmp\probe_s24b\build.bat
  Method: real SChannel server context (self-signed cert, TLS 1.2 only) driven
          against the PRODUCT transport from rtsc_tls.lib / rtsc_tls_schannel.lib,
          complete a real handshake, then call TlsTransport::Shutdown().

  Verbatim output (run 2026-10-23 after batch 0, against post-batch-0 libs):

    --- PART 1: product, handshake complete, Shutdown() ---
      status=0 native=0x00090312 out=201 closed=true
      ASSERTION A: status != kOk ?  FAIL  <-- this is a RED test today
      ASSERTION B: native_code != SEC_I_CONTINUE_NEEDED ?  FAIL  <-- also RED today

  Reading it:
    status = 0            -> Status::kOk
    native_code=0x00090312 -> SEC_I_CONTINUE_NEEDED
    out=201               -> 201 bytes emitted (the renegotiation request)
    closed=true           -> closed_ was set

  So the product reports "closed successfully" while the native code says
  "continue needed" and it emitted 201 bytes of renegotiation traffic. That is
  the S24-b violation, live, on the real backend, with no test-only fixtures.

  Note this run uses the UNFIXED shutdown token (S24-a is still unfixed at batch
  0), which is why SEC_I_CONTINUE_NEEDED appears at all. That is fine: the red
  baseline must be taken on the code as it is, not on a hypothetical.

PART 2 — THE DECISION IS SEPARATELY TESTABLE IN ISOLATION
--------------------------------------------------------------------------
  The same decision, extracted into MapShutdownStatus(), shows the mapping bug
  independently of whether the token is fixed.

  CORRECTION (audit A20-2, 2026-10-23): MapShutdownStatus() is NOT a verbatim
  copy of the product. Its else-branch returns kProtocolError, whereas the real
  product fallthrough (the "shutdown best effort" line) returns kOk. The probe
  models the *decision under test* (does SEC_I_CONTINUE_NEEDED count as
  success?) and deliberately picks the strict answer for the non-success path,
  so that ASSERTION C isolates the one mapping being examined.

  This does not change the verdict: the CONTINUE_NEEDED arm maps to kOk in both
  the product and the probe, which is the defect. But the earlier wording
  "verbatim" was inaccurate and is retracted here.

  Library version used for PART 1: post-batch-0 build, UNFIXED S24-a
  (token still empty), i.e. rtsc_tls.lib + rtsc_tls_schannel.lib as built at
  ts=20261023-092309. closed=true in PART 1 is the unfixed product reading; a
  shadow tree with S24-a fixed reports closed=false. Readers must not compare
  PART 1 numbers across library versions.

    --- PART 2: the mapping function, in isolation ---
      MapShutdownStatus(SEC_I_CONTINUE_NEEDED=0x00090312) = 0
      MapShutdownStatus(SEC_E_OK)                     = 0
      MapShutdownStatus(SEC_E_UNSUPPORTED_FUNCTION)   = 5
      ASSERTION C: MapShutdownStatus(CONTINUE_NEEDED) != kOk ?  FAIL  <-- RED today, GREEN after fixing only :431
